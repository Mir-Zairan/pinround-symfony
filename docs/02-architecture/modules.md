## Why modules

Six months from now, Omar adds a "mute" option to pings. In a classic monolith he would touch the ticket entity, the Home query, and the email code, and break the manager page by accident. In pinround he changes only the Notification module. Home learns about mutes through a small `NotificationQueries` interface. Tickets do not know mutes exist.

That is the goal: **a change in one area stays in one area.** We get it without the cost of microservices, which a team of three cannot run ([ADR-0002](../03-adr/0002-modular-monolith.md)).

## Directory layout and namespaces

Every module has the same five folders:

```text
src/
  SharedKernel/                 # ids, Clock, TenantContext, DomainEvent base, Result, ReadinessCheck, DemoSeedStep, FieldEncryption, RequiresRecentAuth
  Ticketing/
    Api/                        # PUBLIC: interfaces + DTOs other modules may use
      TicketQueries.php
      TicketCommands.php
      Dto/TicketSummary.php
      Event/TicketCreated.php   # public event classes
    Domain/                     # entities, value objects, domain services, repository interfaces
      Ticket.php
      TicketKey.php
      CheckReason.php
      TicketRepository.php
    Application/                # use cases (command handlers, query handlers), Api implementations
      CreateTicket/CreateTicketHandler.php
      ConfirmCheck/ConfirmCheckHandler.php
      TicketQueriesService.php
    Infrastructure/             # Doctrine mappings + repositories, Messenger handlers, external clients
      Doctrine/DoctrineTicketRepository.php
      Doctrine/Mapping/Ticket.orm.xml
    UI/                         # controllers, forms, Twig components, voters, templates for this module
      Controller/TicketController.php
      Voter/TicketVoter.php
      Voter/TicketCreationVoter.php
      templates/
```

Namespaces follow the folders: `App\Ticketing\Domain\Ticket`, `App\Ticketing\Api\TicketQueries`, and so on.

- **Domain** depends on nothing except `SharedKernel`. Doctrine mapping is XML in Infrastructure, so entities stay plain PHP.
- **Application** depends on Domain, on SharedKernel, and on the `Api` of other modules.
- **Infrastructure** implements Domain interfaces.
- **UI** calls Application through command and query classes. It never calls repositories.
- **Api** holds only interfaces, read-only DTOs and event classes. There is no logic in it.

## How modules talk

1. **Synchronous query or command through `Api`.**
   - Example: Ticketing asks Workflow, "may Lena move this ticket from In progress to Code review?" through `Workflow\Api\TransitionPolicy`.
   - The call runs inside the caller's transaction.
2. **Domain events through the outbox.**
   - Example: Ticketing records `TicketMoved`. The event row is written to the outbox in the same transaction. Notification, Audit, Integration and Insight react later ([ADR-0009](../03-adr/0009-async-messaging-and-outbox.md)).
3. **Read model updates that must be instant** run synchronously, in the same transaction.
   - Example: the `ins_ticket_turn` row ([ADR-0015](../03-adr/0015-turn-read-model.md)).
   - The producing module calls `Insight\Api\TurnProjector` directly, so Home is correct right after the click.
4. **Setup steps in the transaction that creates an organization** ([ADR-0036](../03-adr/0036-organization-setup-steps-in-the-creating-transaction.md)).
   - Example: Workflow's `SetUpOrganizationWorkflow` gives every new organization the eight core steps and the default rule set.
   - A module implements `Organization\Api\OrganizationSetupStep`; the `_instanceof` rule in `config/services.yaml` tags it, and Organization's `CreateOrganization` runs every tagged step once the organization row exists, highest tag priority first.
   - The step runs inside the caller's open transaction, whose tenant is already the new organization. It never begins, commits or rolls back a transaction.
   - It records no events of its own, except through the outbox in that same transaction.
   - Anything it throws rolls back the whole organization.
   - Use it only for data an organization cannot exist without. Anything that may arrive a few seconds later reacts to an Organization event instead.
5. **A page embeds another module's Twig component or frame by name.**
   - Example: the ticket page renders `{{ component('ThreadFrame', {key: ticket.key}) }}` and `{{ component('RoundsSection', {key: ticket.key}) }}`.
   - The page passes only SharedKernel values (a key, an id, a string) and imports no class of the other module, so deptrac sees no edge.
   - The embedded component is a heading and a lazy Turbo frame. The frame's own route, in the other module's UI, loads the data for the logged-in viewer from the request alone and decides who may see it with that module's own voter.
6. **Never:**
   - a join across another module's tables (one named exception: Insight's query service may join `ins_ticket_turn` with Ticketing's read-only view `tkt_ticket_list_v`, [ADR-0015](../03-adr/0015-turn-read-model.md));
   - a Doctrine relation to another module's entity (store the id as a value object instead);
   - using another module's repository or `Domain` class.

## Module catalogue

Table prefixes keep ownership visible in SQL. The tables and columns are in [data-model.md](data-model.md).

### SharedKernel

- **Purpose:** the small set of types every module shares.
- **Contains:**
  - id value objects (`OrganizationId`, `UserId`, `TicketId` …, all UUIDv7, [ADR-0006](../03-adr/0006-identifiers.md));
  - `Clock` (an interface, so tests can freeze time);
  - `TenantContext` (the current `OrganizationId`; callers only fill it). The DBAL driver middleware `TenantMiddleware` in `Infrastructure/Doctrine` reads it and runs `set_config('app.org_id', …, true)` at the start of each transaction. `TenantFilter` scopes ORM queries on `TenantOwned` entities and throws `TenantNotSet` without a tenant; `RequestTransaction` wraps each main web request in one transaction, except on a route whose `_request_transaction` default is `false` (the health routes, and the actions that open their own transaction through `Transactions` or Organization's `OrganizationTransactions`); `TenantContext` refuses (`TenantSwitchRefused`) an org switch or `clear()` while a transaction is open or the EntityManager holds an entity ([ADR-0005](../03-adr/0005-multi-tenancy.md), [row-level security](data-model.md#row-level-security));
  - the `DomainEvent` base (event id, occurred at, organization id, actor id);
  - `Result`/`Problem` types for expected failures;
  - `DenyByDefaultVoter` (`UI\Voter`): the base that new voters on a subject extend. It abstains only for an attribute it does not own or a subject of another class, and denies its own unless the subclass's rule grants ([ADR-0013](../03-adr/0013-authorization.md)). The voters whose subject is null are the exceptions, because the base cannot own a null subject, so they keep Symfony's `Voter`: Organization's `OrganizationMemberVoter` (`ORGANIZATION_CHOOSE`) and Identity's `OwnAccountVoter` (`ACCOUNT_EDIT_OWN`); `AdminAreaVoter` extends the base;
  - `RequiresRecentAuth` (`UI`): the attribute that marks a sensitive controller class or action. Identity enforces it: without the password and a two-step code in this session within 10 minutes, the person goes to "Confirm it's you" ([ADR-0012](../03-adr/0012-authentication.md)). It is here because most modules that will mark sensitive actions (Organization, Integration, Audit and others, P08-P11) may not see `Identity_Api`, while every module may see SharedKernel;
  - `RelativeTime` (`UI`): `sinceOf()` ("now", "5 min ago", "3 h ago", then "2 Nov") and `dateOf()`, the time words Ticketing's What happened and tickets list (through `TicketListText`) and Conversation's thread print; here because those UIs may not see each other;
  - `FieldEncryption` (Application, with `UndecryptableField` for a value that is altered, cut short or written with a key no longer in the ring) and its libsodium secretbox implementation `SodiumFieldEncryption` in `Infrastructure/Encryption`, with the key ring `FieldEncryptionKeys` ([ADR-0027](../03-adr/0027-secrets-and-encryption.md), [config.md](../operations/config.md#field-encryption)): encrypts secrets stored in the database. Identity's MFA seeds use it first; Integration's Jira and webhook secrets, OIDC client secrets and AI provider credentials follow;
  - `CitextType` and `TextArrayType` (`Infrastructure/Doctrine`): the Doctrine types of PostgreSQL `citext` and one-dimensional `text[]` columns (`text_array`: Organization's `org_roles`, Identity's `recovery_code_hashes`). Doctrine registers a type once for the whole app, so it cannot belong to one module;
  - `OnceOnlyHandling` (Application: run an async handler's effect once per message), with `MessageIdStamp`, `MessageIdStampMiddleware`, `MessageBeingHandled` and `ProcessedMessageLedger` in `Infrastructure/Messenger` ([ADR-0033](../03-adr/0033-valkey-transports-workers-and-outbox-relay.md#idempotency-key));
  - `Transactions` (Application) with `DoctrineTransactions` (`Infrastructure/Doctrine`): `run(\Closure)` gives an action that runs without the request transaction a transaction of its own under the request's tenant, committed when the closure returns and rolled back, with the EntityManager left closed, when it throws; it refuses with `LogicException`, and does not run the closure, without a tenant or inside an open transaction. Organization's `PeopleController` (the invite), Ticketing's `TeamProjectsController` and Workflow's `TeamWorkflowController` use it. It is here because no module may use another's Application, while every module layer may see SharedKernel. Organization's `OrganizationTransactions::runAs` is not this: it switches to another organization's tenant and back;
  - `ReadinessCheck` (`Infrastructure/Health`): one thing `/health/ready` proves. The module that owns what is checked implements it (Audit: `NextAuditPartitionExists`; Media: `ObjectStorageIsReachable`), and autoconfiguration tags it. SharedKernel holds the platform checks `DatabaseAnswers`, `MigrationsAreCurrent` and `ValkeyAnswers` (one service per Valkey), and `ReadinessCheckFailed` for a dependency that answered in the wrong state ([operations.md](operations.md#observability));
  - `DemoSeedStep` (`Infrastructure/Console`, with `DemoSeedRefused`): one part of the demo data that `app:demo:seed` runs, dev and test only. The module that owns the tables implements it (Identity: `SeedDemoPeople`; Organization from P01.T3: `SeedDemoOrganizations`, priority 50; Ticketing from P02.T1: `SeedDemoProjects`, priority 40), autoconfiguration tags it, and `#[AsTaggedItem(priority: …)]` sets the order, highest first. It lives in SharedKernel because the seed command must not import modules, the same reason as `ReadinessCheck`;
  - `PingClearing` (`Application`, built in P04.T6, FR-PNG-05): `clearForActor(OrganizationId, TicketId, UserId $actor, at): int` clears the actor's open pings on the ticket when the organization's auto-clear is on, marks their ping bell rows done and writes one `PingCleared` (`Acted`) each, all in the caller's open transaction; it locks those pings first, so a second call at once clears none, and refuses with `LogicException` when no transaction is open. Notification's `Application\AutoClear\ClearPingsOnAction` implements it (autowired as the only implementation). Ticketing's `Application\MoveTicket\MoveTicket` calls it right after it saves a move, a move to a step or a give (`TicketCommands::move`, `moveTo` and `giveTo` return its count); Conversation's `PostComment`, `PostReply`, `AskQuestion` and `Answer` call it right after their own write and return `Application\PostedMessage(id, clearedPingCount)`. It is here because neither of them may use Notification's Api;
  - `PingsClearedToast` (`UI`, built in P04.T6, FR-PNG-05): `withClearedPings(string $toast, int $clearedCount): string` adds " 1 ping on this ticket cleared." or " N pings on this ticket cleared." to an action's toast, and returns the toast as it is for 0; `InvalidArgumentException` for a count below 0. Ticketing's `TicketMoveController` and Conversation's `ThreadController` (comment, question, answer and reply toasts) use it. Only two modules need it, an exception to the three-module rule below like `TicketTurnSnapshot`; it is here because Ticketing's UI and Conversation's UI may not see each other, so the toast wording and count pass through SharedKernel;
  - `TicketTurnSnapshot` (`Domain`): one ticket, its step and its team's lead and people, as Ticketing's `TicketTurnQueries::factsOf` and `TicketPageView` carry it and Insight's `TurnProjector::refreshFrom` takes it. Only two modules need it, an exception to the three-module rule below like `AfterCommitTagInvalidation`; it is here because both modules' Apis name it and an Api may see only SharedKernel;
  - `AfterCommitTagInvalidation` with `AfterCommitTagInvalidationMiddleware` (`Infrastructure/Cache`): a tag-aware cache queues the tags of a change, and they are cleared only after the outermost transaction on the default connection commits (dropped on a rollback); it also says under which organization a cache may read and fill entries now. Workflow's `WorkflowCache` and Organization's `TeamPeopleCache` use it. It is here because one DBAL middleware must track the outermost transaction for every tag-aware cache: two copies in two modules would each wrap the connection and could disagree on where the transaction begins and ends;
- **Owns tables:** `processed_message` (global plumbing, no `organization_id`; see [data-model.md](data-model.md)).
- **Rule:** keep it tiny. A type joins SharedKernel only when three or more modules need it.

### Identity (`idn_`)

- **Story:** Sara invites Omar. Omar sets a password and turns on two-factor login. Later the company switches to Microsoft login, and Omar's account is linked, not duplicated.
- **Owns:** `idn_user`, `idn_credential`, `idn_password_reset`, `idn_mfa_secret`, `idn_sso_identity`, `idn_api_token`, `idn_login_attempt`. Sessions live in Valkey.
- **Api:**
  - `CurrentUser::id(): ?UserId` and `CurrentUser::idOf(mixed $tokenUser): ?UserId` (built in P01.T3: the logged-in user of the request, or of the token a voter is given; null when nobody is; `Infrastructure\Security\SymfonyCurrentUser`)
  - `CurrentTimeZone::zone(): \DateTimeZone` (built in P03 for the tickets list: the logged-in user's saved time zone, old IANA names included; UTC when nobody is logged in or no zone is saved; `Infrastructure\Security\SymfonyCurrentTimeZone`)
  - `LoginAssurance::isPasswordSession(mixed $token): bool`, `LoginAssurance::isTwoStepLoginOn(mixed $token): bool` and `LoginAssurance::hasConfirmedTwoStepLoginWithin(mixed $token, int $seconds): bool` (built in P01.T4 and P01.T6 for `AdminAreaVoter` and `SendAdminToTwoStepProof`; true only for the form login's `UsernamePasswordToken` of an Identity user, any other token kind is refused; the last needs two-step login on and a code typed in this session within `$seconds` and not before it was last turned on, the rule `RecentAuth` applies to `RequiresRecentAuth` too; `Infrastructure\Security\SymfonyLoginAssurance`)
  - `LoginAssurance::isTokenAuthenticated(mixed $token): bool` (built in P09.T1 for `UI\Voter\AdminNeedsBrowserSessionVoter` and `UI\Voter\OwnAccountVoter`: true only for the `Infrastructure\Security\ApiTokenAuthentication` that `TokenAuthenticator` creates for a personal access token)
  - `CurrentApiToken::access(): ?ApiTokenAccess` (built in P09.T1 for the scope checks of the MCP tools and the REST API: the token id, the token's organization, its scope names and `expiresAt`, the instant it stops working, in UTC; never the token itself; null for a browser session, for nobody logged in and before the firewall has run; `Infrastructure\Security\SymfonyCurrentApiToken`, which reads the security token)
  - `OrganizationApiTokens` (built in P09.T1 for Organization's Admin › People page; `Application\ApiTokensOfOrganization`; it does not check who asks, as the caller's voter has decided the person is an Admin of the tenant): `livePage(\DateTimeImmutable $now, int $limit, ?\DateTimeImmutable $afterExpiresAt = null, ?string $afterId = null): list<OrganizationApiToken>` gives the tenant's tokens of every person that are neither revoked nor expired, the soonest to expire first (then the lower id), one keyset page after the token the cursor names, in one query; a limit outside 1 to `MAX_PAGE_SIZE` (100), only one half of the cursor or a cursor id that is no UUID throws `\InvalidArgumentException` before any query. `OrganizationApiToken` carries `id`, `ownerId`, `name`, `prefix` and `expiresAt`, never the token or its hash. `revokeAsAdmin(UserId $adminId, string $tokenId, \DateTimeImmutable $now): bool` revokes any token of the tenant, whoever owns it and also an expired one, in the caller's transaction, and publishes `ApiTokenRevoked` with the Admin as actor and the owner as user; false, and nothing published, for a token revoked already; `ApiTokenNotInOrganization` (the page answers 404) for an id that is malformed, unknown or another organization's, with nothing changed
  - `TwoStepProofPages::confirmItsYouPathFor(mixed $request): string` and `::sendToTwoStepSetup(mixed $request, string $notice): string` (built in P01.T6 for `SendAdminToTwoStepProof`: the paths of "Confirm it's you" and of the setup page, each with the way back; `UI\Controller\RecentAuthRedirects`)
  - `UserQueries::byId(UserId): ?UserView`
  - `UserQueries::byIds(list<UserId>): array<string, UserView>` (built in P03 for Insight's turn source and the tickets list: one query on `idn_user` with `= ANY(?::uuid[])`, none for an empty list; keyed by user id string in id order; unknown ids left out, blocked users kept; `UserView` carries `id`, `displayName` and `firstName()`, the first word of the name. Users are global, so it does not limit them to the tenant: callers pass only ids they read under the tenant)
  - `UserQueries::byEmail(string): ?UserView`
  - `UserQueries::emailsOf(list<UserId>): array<string, string>` (built in P04.T8 for Organization's `MemberEmailQueries`: one query on `idn_user`, none for an empty list; the address, trimmed and in lowercase, keyed by user id string in id order; unknown and blocked users left out; at most `MAX_EMAIL_USER_IDS` (100) ids, more throw `\InvalidArgumentException` before any query; not limited to the tenant, like `byIds`)
  - `UserQueries::timeZonesOf(list<UserId>): array<string, \DateTimeZone>` (built in P04.T6 for Organization's `MemberTimeZoneQueries`: one query on `idn_user`, none for an empty list; each person's saved IANA zone keyed by user id string in id order, UTC for a saved zone PHP does not know; unknown ids left out, blocked users kept; at most `MAX_TIME_ZONE_USER_IDS` (100) ids, more throw `\InvalidArgumentException` before any query; not limited to the tenant, like `byIds`)
  - Event `Api\Event\UserRenamed` (built in P03: the user id of a person whose saved display name changed, published by `UpdateProfile` through `Application\IdentityEvents`, `Infrastructure\Messenger\MessengerIdentityEvents`, on event.bus in the transaction of the change; it implements `Api\Event\IdentityEvent`, which goes to the outbox and on to `async_notify` like every other domain event, so other modules handle it only after the commit)
  - Events `Api\Event\ApiTokenIssued` and `Api\Event\ApiTokenRevoked` (built in P09.T1: published by `IssueApiToken` and `RevokeApiToken` through `IdentityEvents` in the write's transaction, the latter only by the revoke that changed the row; ids, scope names and times only, for Audit's `RecordIdentityAuditEntry`)
  - `UserQueries::idByEmail(string): ?UserId` (built in P01.T3 for the demo seed: plain SQL on `idn_user`, null when no one has the address; `Infrastructure\Doctrine\DbalUserQueries`; `byId` and `byEmail` are not built yet)
  - `InvitedPersonRegistration::register(string $email, string $name, string $password, \DateTimeImmutable $now): UserId`, `::minimumPasswordLength(): int`, `::maximumNameLength(): int` and `::isValidEmail(string $email): bool` (the account email rule, which InviteMember asks) (built in P01.T7 for the invite accept page: an active user in UTC and English plus an Argon2id credential, written in the caller's transaction; every refused input comes before any write as `RegistrationRefused` listing `RegistrationRefusal` cases (InvalidEmail, EmailTaken, NameBlank, NameTooLong, PasswordTooShort); an email another transaction took at the same moment gives EmailTaken alone with the EntityManager closed, so the caller rolls back and reads nothing more through the ORM in that request; `Application\RegisterInvitedPerson`)
  - Not an Api: `Infrastructure\Security\TokenAuthenticator` (built in P09.T1, [ADR-0021](../03-adr/0021-mcp-server.md)) authenticates every request of the stateless `api_token` firewall (`/mcp`, `/api/v1`) by its `Authorization: Bearer pr_…` header alone. A live token makes the request its user's, with the token's organization as tenant and an `ApiTokenAuthentication` as security token, and records the token's use at most once a minute; anything else gets the same 401 and leaves no tenant. Other modules read the result through `CurrentApiToken` and `LoginAssurance::isTokenAuthenticated`. `UI\Voter\AdminNeedsBrowserSessionVoter` denies every `ADMIN_*` attribute and `ORG_ADMIN` and `ORG_INVITE` to a token actor; `OwnAccountVoter` denies it `ACCOUNT_EDIT_OWN`
- **Commands:** RegisterInvitedPerson (built in P01.T7, behind `InvitedPersonRegistration`), ChangePassword, StartTwoStepSetup and ConfirmTwoStepSetup (built in P01.T6 step 1: a new seed in `idn_mfa_secret` through `FieldEncryption`, then a code of it turns two-step login on and returns the 10 `RecoveryCodes` once; ports `OneTimeCodes` (`OtphpOneTimeCodes`), `QrCodeImages` (`BaconQrCodeImages`, SVG drawn on the server) and `RecoveryCodeHashing` (`SymfonyRecoveryCodeHashing`, Argon2id)), ConfirmItsYou (built in P01.T6 step 5: the password through `CurrentPasswordCheck`, which shares `ChangePassword`'s limiter, then a code through `AcceptTwoStepCode`; it records the session times `RecentAuth` reads for actions marked `RequiresRecentAuth`), DisableTwoStepLogin (built in P01.T6 step 4: the same password and code checks, then it deletes the `idn_mfa_secret` row and forgets both session times), LinkSsoIdentity, IssueApiToken (built in P09.T1 storage, `Application\IssueApiToken`, not an Api: only Identity's own token page calls it. It returns `Domain\IssuedApiToken`, the saved token and its plain text to show once; at most `MAX_LIVE_TOKENS_PER_USER` (20) tokens that are neither revoked nor expired per person and organization, the 21st refused with `TooManyApiTokens` and nothing added; the count and the insert run under a transaction-scoped advisory lock per organization and person, so it needs the caller's open transaction; ports `Domain\ApiTokens` (`Infrastructure\Doctrine\DoctrineApiTokens`, whose `forUser` lists the newest `MAX_LISTED_TOKENS` (50), revoked and expired ones included, and `liveForUser` only those that still work) and `Domain\ApiTokenHashing` (`Infrastructure\Security\HmacApiTokenHashing`, HMAC-SHA256 keyed by `API_TOKEN_PEPPER`, [ADR-0043](../03-adr/0043-api-token-hash-is-hmac-sha256.md))), RevokeApiToken (built in P09.T1, `Application\RevokeApiToken`, not an Api: a person revokes one of their own tokens in the tenant at once, in the caller's transaction; true only for the call that revoked it, `ApiTokenNotFound` for an id that is malformed, unknown, another person's or another organization's; `RevokeApiToken::asAdmin` is the Admin's revoke behind `OrganizationApiTokens::revokeAsAdmin`, which finds any person's token of the tenant through `ApiTokens::byId`, while `ApiTokens::livePage` reads the Admin's list). Both serve the tokens page, `/me/tokens` (`UI\Controller\TokenController`, linked as "API tokens" from the avatar menu), which lists the person's tokens that still work through `Application\ShowApiTokens::liveOf` over `ApiTokens::liveForUser` (neither revoked nor expired, newest first), makes one behind `RequiresRecentAuth` with `IssueApiToken::issueWithScopeNames` and shows its plain token and the `claude mcp add` line in that response only, each with a Copy button (Stimulus `copy-text`). The form starts with `ApiTokenScope::claudeCodeDefaults` (`read`, `rounds:write`) ticked and offers the other scopes, `reports:write` and `notebooks:write` among them, unticked.
- **Events (planned, not built yet):** `UserRegistered`, `UserLoggedIn`, `LoginFailed`, `MfaEnabled`. `ApiTokenIssued` and `ApiTokenRevoked` are built (see the Api list above). `ConfirmTwoStepSetup` raises no `MfaEnabled` yet: an `aud_event` row needs an organization and Identity is global, so it waits for the Audit consumer of P11 (the same gap as the P01.T2 password-reset audit note).
- **Depends on:** SharedKernel only.
- **ADRs:** [0012](../03-adr/0012-authentication.md), [0021](../03-adr/0021-mcp-server.md), [0027](../03-adr/0027-secrets-and-encryption.md), [0043](../03-adr/0043-api-token-hash-is-hmac-sha256.md).

### Organization (`org_`)

- **Story:** Sara creates the team "Shop" with Lena as lead. She gives Raj the Manager role. Omar is a member of Shop and a viewer in "Mobile".
- **Owns:** `org_organization`, `org_membership` (org roles: admin, manager), `org_team`, `org_team_member` (team role: lead, member, viewer; job: tester, developer, other), `org_invitation`, `org_settings` (ping limits, quiet hours, lead-check switch, triager, step policy, AI policy, retention).
- **Api:**
  - `MembershipQueries::organizationsOf(UserId): list<OrganizationId>` (built in P01.T3, through `resolve_user_orgs`, so it needs no tenant)
  - `MembershipQueries::rolesOf(UserId, OrganizationId): Roles` (built in P01.T4; `Roles` offers `isAdmin()`, `isManager()`, `isLeadOf(TeamId)`, `isMemberOf(TeamId)` and `isViewerOf(TeamId)` for exactly that team role, `isInTeam(TeamId)` for any team role, `teamIds()` in id order, `teamSlugOf(TeamId): ?string` (added in P02.T8: the slug of each team the user has a role in, filled by a join in the same query, so the menu links a person's teams without a team query; null for any other team), and `Roles::none()`, which a user with no membership gets)
  - `MembershipQueries::membersAmong(OrganizationId, list<UserId>): list<UserId>` (built in P03.T7 for the Needs input dialog: in one query on `org_membership`, those of the asked users who are members of that organization, each once, in id order; membership alone counts, so a member with no org or team role is one; an empty list runs no query)
  - `TeamQueries::teamsOf(OrganizationId): list<TeamId>` (moved from `MembershipQueries` in P01.T5; every team of the organization, in id order) and `TeamQueries::summariesOf(OrganizationId, list<TeamId>): list<TeamSummary>` (`TeamSummary` offers `id()`, `name()` and, from P02.T8, `slug()`; the asked teams of that organization ordered by name ignoring case, then id, in one query; unknown ids and ids of another organization are not returned)
  - `TeamQueries::bySlug(OrganizationId, string $slug): ?TeamSummary` (built in P02.T8; one query; null when no team of that organization has the slug, also for a slug of another organization's team). Web's `UI\Controller\TeamController` serves the team page `team_show` at `GET /teams/{slug}` with it: an unknown slug is a 404, a team found still needs `TEAM_VIEW`. - **UI (P02.T8):** `UI\TeamWorkflowController`, three POST routes the Team page posts to, each without the request transaction and inside SharedKernel's port `Application\Transactions::run` (see [SharedKernel](#sharedkernel)): `workflow_team_steps_add` (`POST /teams/{slug}/steps`, `name` and `group`, `STEP_CHANGE_TEAM`), `workflow_team_steps_remove` (`POST /teams/{slug}/steps/remove`, `step_id`, `STEP_CHANGE_TEAM`) and `workflow_team_rules_set` (`POST /teams/{slug}/rules`, `rule` and `is_on` `1` or `0`, anything else a 400; `RULES_CHANGE_TEAM`). - **Depends on:** Organization Api.
- **Note:** Workflow does not store tickets. Ticketing owns the ticket's current step and asks Workflow before every move.
- **New organizations:** `Application\SetUpOrganizationWorkflow`, an `Organization\Api\OrganizationSetupStep`, adds the eight core steps and the default rule set in the transaction that creates the organization ([ADR-0036](../03-adr/0036-organization-setup-steps-in-the-creating-transaction.md)); organizations made before that got them from the backfill migration `Version20261110140000`.

### Conversation (`cnv_`)

- **Story:** Lena asks Mia, "Which contract was it?" The ticket pauses. Mia answers from "My reports", and the ticket goes back to its step.

## Event catalogue

All events extend `SharedKernel\DomainEvent`. Every event carries `eventId`, `occurredAt`, `organizationId` and `actorId`. Until SharedKernel has that base, the Organization events implement `Organization\Api\Event\OrganizationEvent` (`organizationId`, `actorId`: the acting user's id or null for the system, `occurredAt`), and the message's `MessageIdStamp` stands in for `eventId`. "Outbox" means the event is stored in the same transaction and delivered at least once to async handlers.

|---|---|---|---|---|
| TicketCreated | Ticketing | Insight, Notification, Audit, Assist, Integration | ticketId, projectId, teamId?, reporterId, assigneeId?, checkReasons[] | outbox |
| TicketMoved | Ticketing | Insight, Notification, Audit, Integration | ticketId, key, fromStepId, toStepId, verb? (the Workflow verb's code, for example `start_work`; null for a lead's "Move to another step…"), movedAt (stands in for `occurredAt`) | outbox (turn row synchronous) |
| TicketAssigned | Ticketing | Insight, Notification, Audit | ticketId, assigneeId, previousId? | outbox |

Rules:

- **An event is a fact in the past tense.** It never asks someone to do something.
- **Consumers must be idempotent.** Wrap the effect in `OnceOnlyHandling::runOnce`, keyed by the `MessageIdStamp` id and a stable handler name, or upsert by natural key ([ADR-0033](../03-adr/0033-valkey-transports-workers-and-outbox-relay.md#idempotency-key)).
- **Event classes are public** (they live in `Api/Event`). Changing a payload means adding fields only. To remove a field, create a new event version.

## Deptrac rules

`composer deptrac` runs in `composer qa` and in CI ([ADR-0028](../03-adr/0028-testing-and-quality-gates.md)). The one hand-written config is `deptrac.yaml`. It analyses `src` only and runs with `--fail-on-uncovered --report-uncovered`: a class that is outside every layer (and is not a PHP built-in) fails the run. The call edges between modules are the "Depends on" lines in the catalogue above, as decided in [ADR-0032](../03-adr/0032-module-call-edges-follow-modules-catalogue.md).

**Layers.** Layers are collected by namespace regex (for example `^App\\Ticketing\\Domain\\`), not by folder.

- Per module M, six layers: `M_Api` (`App\M\Api\`, except `Api\Event\`), `M_Event` (`App\M\Api\Event\`), `M_Domain`, `M_Application`, `M_Infrastructure`, `M_UI`. The modules are Identity, Organization, Workflow, Ticketing, Conversation, Review, Media, Notification, Insight, Assist, Integration, Audit, AgentApi and Web.
- `SharedKernel`: `App\SharedKernel\`.
- `Vendor`: every class that is not `App\`, not `Symfony\AI\` and not a PHP built-in.
- `SymfonyAi`: `Symfony\AI\` (Symfony AI is beta, [ADR-0018](../03-adr/0018-ai-provider-abstraction.md)).
- `Assist_AiPlatform`: `App\Assist\Infrastructure\Platform\`. This folder is cut out of `Assist_Infrastructure`, which collects the rest of `App\Assist\Infrastructure\`.
- `Kernel`: `App\Kernel` only.

**Rules.** D(M) is the set of modules in M's "Depends on" line in the catalogue above. U(M) is the part of D(M) the line names as "X Api (UI only: …)": only M's UI may call those. E is the `Event` layer of every module, including M's own. Anything not listed fails the build.

| From | May depend on |
|---|---|
| `M_Api` | `SharedKernel` |
| `M_Event` | `SharedKernel` |
| `M_Domain` | `SharedKernel` |
| `M_Application` | `M_Domain`, `M_Api`, `SharedKernel`, `(D(M) − U(M))_Api`, E |
| `M_Infrastructure` | `M_Domain`, `M_Application`, `M_Api`, `SharedKernel`, `Vendor`, `(D(M) − U(M))_Api`, E |
| `M_UI` | `M_Application`, `M_Api`, `SharedKernel`, `Vendor`, `D(M)_Api` |
| `Assist_AiPlatform` | `Assist_Domain`, `Assist_Application`, `Assist_Api`, `SharedKernel`, `Vendor`, `SymfonyAi` |
| `SharedKernel` | `Vendor` |
| `Kernel` | `Vendor`, `SharedKernel` |

- Calls into another module go through `D(M)_Api` only, and only for modules in M's "Depends on" line; a module marked "(UI only: …)" there only from M's UI (so far Assist's Identity Api).
- Any module's Application and Infrastructure may use any module's event classes (E), so a module can listen to events of modules it does not call. UI may not use events.
- Only Infrastructure and UI get `Vendor`. Api, Event, Domain and Application do not.
- Only `src/Assist/Infrastructure/Platform` (`Assist_AiPlatform`) may depend on `Symfony\AI\*`. No other layer or module may, not even the rest of Assist's Infrastructure, although it gets `Vendor`. `Assist_AiPlatform` gets no other module's Api and no events.
- No module may touch another module's Domain, Application, Infrastructure or UI.

**Tests.** `tests/Unit/Architecture/DeptracConfigTest.php` checks that every `src/` folder has its six layers, every module layer has a folder, every layer in the ruleset exists, only Infrastructure and UI get `Vendor`, Application and Infrastructure get every Event layer, each module's Application, Infrastructure and UI get exactly the other Apis of its "Depends on" line (a "UI only" one in UI alone), only `Assist_AiPlatform` gets `SymfonyAi` (with exactly the layers in the table above), and `Vendor` and `Assist_Infrastructure` leave out `Symfony\AI\` and the Platform folder. `tests/Unit/Architecture/ModuleSkeletonTest.php` checks that every module folder holds exactly `README.md` and the five layer folders. `tests/Integration/Architecture/ModuleBoundaryViolationTest.php` runs Deptrac with the arguments of the `deptrac` composer script on four fixtures in `tests/Fixtures/Deptrac`: `ReviewUsesTicketingDomain` must fail with `Review_Application on Ticketing_Domain`, `ReviewUsesUncoveredClass` must fail as uncovered, `AuditUsesTicketingApi` must fail with `Audit_Infrastructure on Ticketing_Api` (Ticketing is not on Audit's "Depends on" line), and `AllowedDependencies` (Review Application using Ticketing Api, Audit Infrastructure using a Ticketing event) must pass. Each fixture config imports the real `deptrac.yaml`; Deptrac merges the `paths` of imported files and resolves them against the importing file's folder, so `./src` points at the fixture. `tests/Integration/Architecture/SymfonyAiImportRuleTest.php` runs Deptrac the same way on two more fixtures there: `SymfonyAiOutsidePlatform` (Assist's `Infrastructure\Prompt` and Ticketing's Infrastructure use Symfony AI) must fail with `Assist_Infrastructure on SymfonyAi` and `Ticketing_Infrastructure on SymfonyAi`, and `SymfonyAiInPlatform` (the Platform folder using Symfony AI, Assist Application and other vendor code) must pass.

## Rules for adding a module

Add a module only if **all** of these are true:

1. It owns data that no current module owns, and it has its own words (a new part of the glossary).
2. Its rules change for different reasons than its neighbours' rules.
3. You can name its Api in five methods or fewer at the start.

Then:

- write an ADR or update [ADR-0002](../03-adr/0002-modular-monolith.md);
- pick a table prefix;
- add both Deptrac layers;
- add it to this catalogue and to the event catalogue;
- add tenant-isolation tests for its tables ([ADR-0005](../03-adr/0005-multi-tenancy.md)).

If you are unsure, put the feature inside the closest module first. Moving code out later is cheaper than merging two modules back together.
