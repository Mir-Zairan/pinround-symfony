# Media

Screenshot uploads and processing: presigned uploads, checks, cleaning and small WebP variants. It is generic and knows nothing about tickets. It owns the tables `med_object` and `med_upload_intent`. Its Api is `Uploads`, `MediaQueries` and `SignedUrls`. `Infrastructure\Health\ObjectStorageIsReachable` tells `/health/ready` whether the object storage is reachable. It may use the Api of SharedKernel only.

Status: the two tables exist (`Version20261115120000`, with row-level security) and are mapped by `UploadIntent` and `MediaObject`. The domain ports `UploadIntents` and `MediaObjects` are stored through `Infrastructure\Doctrine\DoctrineUploadIntents` and `DoctrineMediaObjects`; `recordUse` lets an upload intent be used once only, even by two requests at once. The storage services are `ObjectStorageFilesystemFactory`, `PresignedUploads`, `UploadKey` and `ObjectStorageSettings`; they need the six `OBJECT_STORAGE_*` variables (`ENDPOINT`, `PUBLIC_URL`, `BUCKET`, `REGION`, `ACCESS_KEY_ID`, `SECRET_ACCESS_KEY`). The upload routes are built: `POST /media/intents` and `POST /media/intents/{id}/complete` (`UploadIntentController`, guarded by `UploadVoter`). `Uploads::begin` checks the policy (`UploadPolicy`: PNG, JPEG or WebP, up to 15 MB) and returns a presigned PUT slot for an `UploadTarget`; the intent stores `target_kind` and `target_id` (`Version20261115140000`). `Uploads::complete` checks the stored target again, marks the intent used and writes `ProcessUpload(organizationId, mediaId)` to the outbox in the same transaction (`MessengerUploadProcessingQueue`); the relay sends it to `async_media`. A module that owns a target kind implements `MediaTargetAuthorizer` (Ticketing: `TicketMediaTarget`). `ProcessUpload` has no handler yet; the processing worker is P05.T2.
