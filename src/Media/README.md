# Media

Screenshot uploads and processing: presigned uploads, checks, cleaning and small WebP variants. It is generic and knows nothing about tickets. It owns the tables `med_object` and `med_upload_intent`. Its Api is `Uploads`, `MediaQueries`, `SignedUrls` and `UploadedMedia`. `Infrastructure\Health\ObjectStorageIsReachable` tells `/health/ready` whether the object storage is reachable. It may use the Api of SharedKernel, and Organization's Api (`CurrentActor`, the request's actor) in Application, Infrastructure and UI.

Status: the two tables exist (`Version20261115120000`, with row-level security) and are mapped by `UploadIntent` and `MediaObject`. The domain ports `UploadIntents` and `MediaObjects` are stored through `Infrastructure\Doctrine\DoctrineUploadIntents` and `DoctrineMediaObjects`; `recordUse` lets an upload intent be used once only, even by two requests at once. The storage services are `ObjectStorageFilesystemFactory`, `PresignedUploads`, `UploadKey` and `ObjectStorageSettings`; they need the six `OBJECT_STORAGE_*` variables (`ENDPOINT`, `PUBLIC_URL`, `BUCKET`, `REGION`, `ACCESS_KEY_ID`, `SECRET_ACCESS_KEY`). The upload routes are built: `POST /media/intents` and `POST /media/intents/{id}/complete` (`UploadIntentController`, guarded by `UploadVoter`). `Uploads::begin(OrganizationId, UserId, UploadTarget, purpose, mime, bytes, at)` checks the policy (`UploadPolicy`: PNG, JPEG or WebP, up to 15 MB, at most `MAX_OPEN_UPLOADS_PER_USER` = 20 open uploads per person), refuses an upload that does not fit the organization's storage quota (stored objects plus open intents, summed in one statement through the `StorageQuota` port, under a per-organization advisory lock; covering indexes in `Version20261115160000`), asks the target's authorizer again and returns a presigned PUT slot for an `UploadTarget`; the intent stores `target_kind` and `target_id` (`Version20261115141000`). `Uploads::complete(OrganizationId, UserId, intentId, at)` (implemented by `DirectUploads`) checks the stored target again, marks the intent used and writes `ProcessUpload(organizationId, mediaId)` to the outbox in the same transaction (`MessengerUploadProcessingQueue`); the relay sends it to `async_media`. A module that owns a target kind implements `MediaTargetAuthorizer` (Ticketing: `TicketMediaTarget`), which decides for the request's actor only. `ProcessUpload` is handled in worker-media by `Application\Processing\CleanUpload` (`Infrastructure\Messenger\ProcessUploadHandler`): it checks the size (a HEAD), the signature, the declared type, the size in the header (`PurePhpImageHeaderReader`, at most 40 megapixels and 16,384 px a side) and animation before it reads the whole file, reuses the variants of a picture the organization has ready already (sha256), re-encodes any other through the `ImageEncoder` port into a WebP view (up to 1,920 px) and thumb (up to 480 px), deletes the upload object and publishes `MediaReady` or `MediaRejected` (`MessengerMediaEvents`, outbox), once per message. The port is implemented by `Infrastructure\Processing\VipsImageEncoder`, which runs the `vips` tool of the image's `libvips-tools` package through `symfony/process` (decode with the format's own loader and `--fail-on error`, then `thumbnail` to WebP, keeping only the picture chunks; media-pipeline.md, Processing worker). A refusal (any exit code but 0, 126 and 127), a crash signal (SIGILL, SIGABRT, SIGBUS, SIGFPE, SIGSEGV) or a 30 s timeout rejects the object as unreadable; a tool that cannot start (exit code 126 or 127) or is stopped by any other signal (SIGKILL) leaves it pending for the retry. vips inherits only `PATH`, `HOME`, `TMPDIR` and `LANG`. The test environment binds `FakeImageEncoder`; the `libvips` test group runs the real tool, in CI in the dev image (the `build` job). `SignedUrls::forVariants(OrganizationId, mediaIds, variant, at)` (implemented by `Application\SignedVariantUrls`, signing through `MediaUrlSigner` = `Infrastructure\Storage\PresignedDownloads`) reads up to `MAX_MEDIA_IDS` = 200 objects in one query and answers a `MediaImage` per id (`MediaImageStatus` pending, ready with a signed URL, or rejected with its reason). The caller has already decided that the viewer may see what the pictures belong to; Media takes no user. Signing times are rounded down to the minute and a URL works 5 minutes from there, so renders in one minute give the same URL; the URL asks the storage for `Cache-Control: private, max-age=240, immutable` (ADR-0041).

`UploadedMedia::statesOf(OrganizationId, UserId, mediaIds)` (implemented by `Application\UploaderMediaStates` over `MediaObjects::byIds`) answers `MediaImageStatus` pending, ready or rejected for the pictures that person uploaded, up to `MAX_MEDIA_IDS` = 50 in one query; any other id is left out. `GET /media/{id}/status` (`UploadStatusController`, uploader only, 404 for anything else, `no-store`, 120 a minute per person through `media_upload_status_per_user`) serves it to the form that waits for its screenshot (media-pipeline.md, Upload status).
