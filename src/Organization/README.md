# Organization

Organizations, teams, members, roles, invitations and settings such as ping limits and AI policy. It owns the tables `org_organization`, `org_membership`, `org_team`, `org_team_member`, `org_invitation` and `org_settings`. Its Api is `MembershipQueries`, `CurrentActor`, `TeamQueries`, `InvitationQueries`, `OrgSettings` and the voter attributes `OrganizationPermission`, `TeamPermission` and `AdminPermission`, and its events in `Api\Event` (`MemberJoined`, `MemberInvited` with no email, `OrgRolesChanged`, `TeamCreated`, `TeamRoleChanged`, all `OrganizationEvent`), which go through the outbox to `async_notify`. `MembershipQueries::rolesOf` gives one user's `Roles` in an organization (`isAdmin`, `isManager`, `isLeadOf`, `isMemberOf` and `isViewerOf` for exactly that team role, `isInTeam` for any, `teamIds`; `Roles::none()` without a membership); `DbalMembershipQueries` reads it under row-level security with no cache, so it needs an open transaction under that organization as tenant and finds nothing otherwise. `TeamQueries::teamsOf` gives that organization's team ids and `summariesOf` the id and name of the asked ones, ordered by name, `allSummariesOf` those of every team in one query and `countOf` how many there are; `DbalTeamQueries` reads all four the same way. `CurrentActor::actorFor` gives a voter the `ActorContext` (user id, organization id, `Roles`) of the token user it is given in the request's tenant, or null without either; `Infrastructure\Security\RequestScopedCurrentActor` builds it once per request for each user and organization and the kernel resets it between requests, so role changes take effect at the next request. `InvitationQueries::pendingOf(OrganizationId, limit, after)` gives one keyset page of the invitations not accepted and not expired, newest first by `created_at` then id, at most `MAX_LIMIT` (100) and throwing `InvalidArgumentException` outside 1..100; `PendingInvitation` offers `id()` (a string), `email()`, `invitedAt()` and `expiresAt()`, and `DbalInvitationQueries` reads under row-level security like the other queries. Its commands in `Application` (`CreateOrganization`, `AddMember`, `InviteMember`, `AcceptInvitation`, `SetOrgRoles`, `CreateTeam`, `SetTeamRole`) write in the caller's transaction and publish their events through `OrganizationEvents` (`Infrastructure\Messenger\MessengerOrganizationEvents`). InviteMember refuses an existing member and replaces an open invitation of the same email; a concurrent second invite gets `InvitationAlreadyOpen`. `Application\InvitationLinks::find(token)` (`Infrastructure\Doctrine\DbalInvitationLinks`) turns an emailed link into an `OpenInvitationLink` for the accept page: it resolves the token's SHA-256 through `resolve_invitation` without a tenant, then reads the open invitation under its organization in a short transaction, so it needs no transaction open. `AcceptInvitation::acceptAs` (the logged-in account with the invited email) and `acceptAsNewPerson` (registers the person through Identity's `InvitedPersonRegistration` first) take that link and the link token, lock the invitation row and check the token against its stored hash, as anyone can build an `OpenInvitationLink`; then the person joins with the invited org roles and, for a team invitation, the team role with job Other. Their refusals are Application exceptions the UI may catch: `InvitationNoLongerValid`, `InvitationForAnotherPerson` and `AlreadyJoined`, plus Identity's `RegistrationRefused`. When `MemberInvited` arrives on event.bus in worker-notify, `Infrastructure\Messenger\QueueInvitationLinkEmailHandler` puts `Application\EmailInvitationLink` (organization id and invitation id, never the token) on the command bus, routed to `async_notify`. `Infrastructure\Messenger\EmailInvitationLinkHandler` (command.bus) runs `SendInvitationLink` in its own transaction, apart from the `member.invited` audit entry. It loads the invitation with `Invitations::lockById` (a row lock), makes the link token, stores only its SHA-256 on the invitation and then emails `/invite/{token}` through `InvitationMailer` (`Infrastructure\Mail\SymfonyInvitationMailer`). It skips an invitation that is gone, no longer open or already has a link token, so no invitation gets a second link, even if `EmailInvitationLink` is queued twice, unless the email was sent and the transaction then failed to commit. SetOrgRoles locks the organization's admins and SetTeamRole the team before changing anything, so concurrent changes keep an admin and one lead. Built so far in `UI`: `EnterChosenOrganization` sets each web request's tenant from the organization chosen in the session, checked against `MembershipQueries::organizationsOf` (`resolve_user_orgs`), and `/org/choose` (`OrganizationChoiceController`, checked by `OrganizationMemberVoter`) lets a user choose or switch. `InvitationController` is the invite accept page: `/invite/{token}` moves the token into the session and redirects to `/invite`, which checks the link with `InvitationLinks::find`, asks `ORG_ACCEPT_INVITATION`, and runs `AcceptInvitation` through `Application\OrganizationTransactions::runAs` (`Infrastructure\Doctrine\DoctrineOrganizationTransactions`), a transaction of its own under the link's organization that is refused while one is open; then the person goes to Home under that organization, or to the login page after creating an account. `UI\Voter\OrganizationVoter` decides `ORG_VIEW` (the organization the request works in, which EnterChosenOrganization sets only for a member), `ORG_ADMIN` (an Admin there) and `ORG_INVITE` (an Admin only; admin pages also ask `ADMIN_AREA`); `UI\Voter\TeamVoter` decides `TEAM_VIEW` (any team role in the team, or Admin or Manager of its organization) and `TEAM_LEAD` (only the team's Lead), reading the organization's teams at most once per request; `UI\Voter\AdminAreaVoter` decides `ADMIN_AREA` (an Admin of the request's organization with a password session, two-step login on and a code typed in this session within the last hour, `ADMIN_STEP_UP_SECONDS`, all from Identity's `LoginAssurance`); `UI\Voter\InvitationVoter` decides `ORG_ACCEPT_INVITATION` on an `OpenInvitationLink` (the logged-in account with the invited email, or nobody logged in when no account has that email yet). All four extend SharedKernel's `DenyByDefaultVoter`. `UI\SendAdminToTwoStepProof` turns a refused `ADMIN_AREA` of such an Admin into a redirect, through Identity's `TwoStepProofPages`: to the setup page while two-step login is off, else to "Confirm it's you"; anyone else keeps the 403. The demo seed step `Infrastructure\Demo\SeedDemoOrganizations` creates Acme Foods, its teams and Beta Bakery through these commands. It may use the Api of Identity.
