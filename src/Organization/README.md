# Organization

Organizations, teams, members, roles, invitations and settings such as ping limits and AI policy. It owns the tables `org_organization`, `org_membership`, `org_team`, `org_team_member`, `org_invitation` and `org_settings`. Its Api is `MembershipQueries`, `CurrentActor`, `TeamQueries`, `TeamPeopleQueries` (a team's lead and members with their names, jobs and which one leads in one call, cached per team by `Infrastructure\Cache\TeamPeopleCache` and cleared after the commit of a `TeamRoleChanged` and again when it is relayed, and for a renamed person when Identity's relayed `UserRenamed` reaches `ForgetRenamedPersonHandler` in worker-notify, so the old name shows until then; see modules.md), `SettingsQueries`, `PingSettingsQueries`, `AiSettingsQueries` (`aiSettingsOf` gives the AI settings without the provider key and reads AI off on anything it does not know; `providerKeyOf` gives the decrypted provider key for the AI gateway only and throws `UndecryptableField` when a stored key cannot be read; see modules.md), `InvitationQueries`, `DemoOrganizations` (dev and test demo data only), `OrganizationSetupStep` (implemented by other modules, such as Workflow's `SetUpOrganizationWorkflow`; `CreateOrganization` runs each one in the transaction that creates the organization, [ADR-0036](../../docs/03-adr/0036-organization-setup-steps-in-the-creating-transaction.md)) and the voter attributes `OrganizationPermission`, `TeamPermission` and `AdminPermission`, and its events in `Api\Event` (`MemberJoined`, `MemberInvited` with no email, `OrgRolesChanged`, `TeamCreated`, `TeamRoleChanged`, `SettingsChanged` with the setting's path in `org_settings.data` and its value before and after, all `OrganizationEvent`), which go through the outbox to `async_notify`. `MembershipQueries::rolesOf` gives one user's `Roles` in an organization (`isAdmin`, `isManager`, `isLeadOf`, `isMemberOf` and `isViewerOf` for exactly that team role, `isInTeam` for any, `teamIds`, `teamSlugOf` for the slug of a team the user has a role in, null for any other; `Roles::none()` without a membership); `DbalMembershipQueries` reads it under row-level security with no cache, so it needs an open transaction under that organization as tenant and finds nothing otherwise. `MembershipQueries::membersAmong` gives, in one query read the same way, those of the asked users who are members of the organization, each once, in id order (an empty list runs no query); the Needs input dialog uses it. `TeamQueries::teamsOf` gives that organization's team ids and `summariesOf` the id, name and slug of the asked ones, ordered by name, `allSummariesOf` those of every team in one query, `countOf` how many there are, `bySlug` the summary of the team with that slug (null for an unknown slug or another organization's team) and `jobOf` one person's `MemberJob` in one team (null when they are not in it or it is another organization's), `leadOf` the team's lead (null only for an unknown team or another organization's), and `possibleAssigneesOf` the leads and members of several teams in one query, by team id, viewers left out (the new ticket form's "Give it to"); `DbalTeamQueries` reads all eight the same way, and it and `DbalTeamPeopleQueries` pick and map team member rows through one `Infrastructure\Doctrine\TeamMemberRows`. `SettingsQueries::stepPolicyOf` gives the organization's `StepPolicy` (`Locked`, `Extend` or `Team`) in one query, `Extend` when there is no settings row or no step policy, and throws `LogicException` for a stored value it does not know; `SettingsQueries::triagerOf` gives the `UserId` of `data.triager_id`, null when there is no settings row or no triager; `DbalSettingsQueries` reads both under row-level security too. `PingSettingsQueries::pingLimitHoursOf` gives `data.ping_limit_hours` (1, 4, 8 or 24) in one uncached query (`Infrastructure\Doctrine\DbalPingSettingsQueries`, under row-level security too), 4 when there is no settings row or no ping limit, and throws `LogicException` for any other stored value; it is a port of its own so the `SettingsQueries` doubles stay as they are. The autowired `SettingsQueries` is `Infrastructure\Doctrine\RequestScopedSettingsQueries`, which keeps each answer per organization and tenant until the kernel's reset, so the Team page reads the policy once; Workflow's `AddStep` and `SetRule` are given `DbalSettingsQueries` (services.yaml), because they check the policy again in their own transaction. `CurrentActor::actorFor` gives a voter the `ActorContext` (user id, organization id, `Roles`) of the token user it is given in the request's tenant, or null without either; `Infrastructure\Security\RequestScopedCurrentActor` builds it once per request for each user and organization and the kernel resets it between requests, so role changes take effect at the next request. `InvitationQueries::pendingOf(OrganizationId, limit, after)` gives one keyset page of the invitations not accepted and not expired, newest first by `created_at` then id, at most `MAX_LIMIT` (100) and throwing `InvalidArgumentException` outside 1..100; `PendingInvitation` offers `id()` (a string), `email()`, `invitedAt()` and `expiresAt()`, and `DbalInvitationQueries` reads under row-level security like the other queries. Its commands in `Application` (`CreateOrganization`, `AddMember`, `InviteMember`, `AcceptInvitation`, `SetOrgRoles`, `CreateTeam`, `SetTeamRole`, `ChangeStepPolicy`) write in the caller's transaction and publish their events through `OrganizationEvents` (`Infrastructure\Messenger\MessengerOrganizationEvents`). `ChangeStepPolicy` changes only the step policy, through `OrgSettingsStore::save`, whose version check fails when another transaction changed the settings meanwhile; the caller asks `ORG_ADMIN` first, and it records no event yet. `ChangeAiSettings` changes the AI settings of the Admin › AI tab: `changeSetting` stores one choice of `OrgSettings::AI_CHOICES` (refusing any other with `ChangeAiSettingsRefused`) and publishes `SettingsChanged` only when the value differs; `changeProviderKey` trims, checks (`ChangeAiSettingsRefused`: missing, over `PROVIDER_KEY_MAX_LENGTH` (512) characters, or not printable ASCII without spaces) and encrypts the organization's own provider key, and every save publishes `SettingsChanged` for `ai.provider_key` from null to "changed", never the key; both save through `OrgSettingsStore::save` with its version check, and the caller asks `ADMIN_AREA` and `ADMIN_AI` first. InviteMember replaces an open invitation of the same email and refuses with Application exceptions the UI may catch: `InvalidEmailAddress` (asked of Identity's `InvitedPersonRegistration::isValidEmail`, the rule an account's email follows), `AlreadyInTheOrganization` (an existing member), and `InvitationSentMeanwhile` when a concurrent second invite of the email was saved first (nothing is recorded; the caller rolls back). `withoutRoles` is the People page's entry. The People page is `PeopleController` (`UI\Admin`): `GET /admin/people` (`organization_admin_people`) shows the organization's people (P14.T3, read only: name, Admin and Manager tags, one "job · team · team role" line per team, the job left out when it is Other, 20 at a time with Show more on `people_after`, the user id of the last person shown; a `people_after` that is no user id is a 400, one of someone who is not a member a 404), read through `Application\OrganizationPeopleQueries::pageOf` (`Infrastructure\Doctrine\DbalOrganizationPeopleQueries`, by display name ignoring case then user id, in three queries whatever the page holds; names live only in Identity, so the order is made in PHP over every member's name, see modules.md), the invite form, the invites not joined yet (20 at a time, Show more with `after_invited_at` and `after_id`) and the API tokens section (P09.T1): every person's live token of the organization from Identity's `OrganizationApiTokens::livePage`, with its owner's name, token name, display prefix and expiry, the soonest to expire first, 20 at a time with Show more on `tokens_after_expires_at` and `tokens_after_id`; each Show more keeps the other lists' cursors, and a half or invalid cursor of any list is a 400. The GET asks `ADMIN_AREA`, `ORG_INVITE` and `ORG_ADMIN`. `GET /admin/people/invite` (`organization_admin_people_invite_page`) asks `ADMIN_AREA` and redirects to the People page, so the form's address opened by hand is no 405 page. `POST /admin/people/invite` (`organization_admin_people_invite`) invites an email with no roles and no team; it asks `ADMIN_AREA` then `ORG_INVITE` and runs outside the request transaction, in one of its own through SharedKernel's `Transactions`. `POST /admin/people/tokens/{id}/revoke` (`organization_admin_people_token_revoke`) asks `ADMIN_AREA` then `ORG_ADMIN` and revokes any person's token in the request transaction through `OrganizationApiTokens::revokeAsAdmin`; a malformed id, an unknown one or another organization's token is a 404 (`ApiTokenNotInOrganization`), an expired form shows the page with a 422, and the redirect goes back to the pages of the lists the form names in the same five cursor fields, validated like the GET's. Each Revoke button's accessible name names the owner, token name and prefix. A toast flashed by the redirect shows once and goes after 3.6 s. The Admin › AI tab is `AiSettingsController` (`UI\Admin`): `GET /admin/ai` (`organization_admin_ai`) asks `ADMIN_AREA` and shows the settings as `AiSettingsQueries` reads them and only whether a provider key is saved; `POST /admin/ai` (`organization_admin_ai_change`) changes one setting at once, with no save button, and `POST /admin/ai/provider-key` (`organization_admin_ai_provider_key`, also `RequiresRecentAuth`) saves the key; both POSTs ask `ADMIN_AREA` then `ADMIN_AI` and run outside the request transaction, in one of their own, answering 422 for a refused value or an expired form and 409 when another save of the settings won the race. The admin shell is Web's (`GET /admin`, `web_admin`, its tab rail `AdminTabRail` and `@Web/admin/layout.html.twig`, see modules.md), so P11 can add tabs of other modules; the People and AI templates extend that layout and fill its `admin_tab` block. The People and AI tabs share their layout in `assets/styles/admin-tab.css`. `Application\InvitationLinks::find(token)` (`Infrastructure\Doctrine\DbalInvitationLinks`) turns an emailed link into an `OpenInvitationLink` for the accept page: it resolves the token's SHA-256 through `resolve_invitation` without a tenant, then reads the open invitation under its organization in a short transaction, so it needs no transaction open. `AcceptInvitation::acceptAs` (the logged-in account with the invited email) and `acceptAsNewPerson` (registers the person through Identity's `InvitedPersonRegistration` first) take that link and the link token, lock the invitation row and check the token against its stored hash, as anyone can build an `OpenInvitationLink`; then the person joins with the invited org roles and, for a team invitation, the team role with job Other. Their refusals are Application exceptions the UI may catch: `InvitationNoLongerValid`, `InvitationForAnotherPerson` and `AlreadyJoined`, plus Identity's `RegistrationRefused`. When `MemberInvited` arrives on event.bus in worker-notify, `Infrastructure\Messenger\QueueInvitationLinkEmailHandler` puts `Application\EmailInvitationLink` (organization id and invitation id, never the token) on the command bus, routed to `async_notify`. `Infrastructure\Messenger\EmailInvitationLinkHandler` (command.bus) runs `SendInvitationLink` in its own transaction, apart from the `member.invited` audit entry. It loads the invitation with `Invitations::lockById` (a row lock), makes the link token, stores only its SHA-256 on the invitation and then emails `/invite/{token}` through `InvitationMailer` (`Infrastructure\Mail\SymfonyInvitationMailer`). It skips an invitation that is gone, no longer open or already has a link token, so no invitation gets a second link, even if `EmailInvitationLink` is queued twice, unless the email was sent and the transaction then failed to commit. SetOrgRoles locks the organization's admins and SetTeamRole the team before changing anything, so concurrent changes keep an admin and one lead. Built so far in `UI`: the team page `GET /teams/{slug}` (`team_show`) is Web's `TeamController`, not this module's. `EnterChosenOrganization` sets each web request's tenant from the organization chosen in the session, checked against `MembershipQueries::organizationsOf` (`resolve_user_orgs`); on the stateless `api_token` firewall (`/mcp`, `/api/v1`) Identity's `TokenAuthenticator` has already set the token's organization, and `EnterChosenOrganization`, reading it through Identity's `CurrentApiToken`, confirms the user is still a member without touching the session, or clears the tenant and answers 401 with `NOT_A_MEMBER_OF_THE_TOKENS_ORGANIZATION`. And `/org/choose` (`OrganizationChoiceController`, checked by `OrganizationMemberVoter`) lets a user choose or switch. `InvitationController` is the invite accept page: `/invite/{token}` moves the token into the session and redirects to `/invite`, which checks the link with `InvitationLinks::find`, asks `ORG_ACCEPT_INVITATION`, and runs `AcceptInvitation` through `Application\OrganizationTransactions::runAs` (`Infrastructure\Doctrine\DoctrineOrganizationTransactions`), a transaction of its own under the link's organization that is refused while one is open; then the person goes to Home under that organization, or to the login page after creating an account. `UI\Voter\OrganizationVoter` decides `ORG_VIEW` (the organization the request works in, which EnterChosenOrganization sets only for a member), `ORG_ADMIN` (an Admin there) and `ORG_INVITE` (an Admin only; admin pages also ask `ADMIN_AREA`), and a personal access token is denied both, and every `ADMIN_*`, by Identity's `AdminNeedsBrowserSessionVoter`; `UI\Voter\TeamVoter` decides `TEAM_VIEW` (any team role in the team, or Admin or Manager of its organization) and `TEAM_LEAD` (only the team's Lead), reading the organization's teams at most once per request; `UI\Voter\AdminAreaVoter` decides `ADMIN_AREA` (an Admin of the request's organization with a password session, two-step login on and a code typed in this session within the last hour, `ADMIN_STEP_UP_SECONDS`, all from Identity's `LoginAssurance`); `UI\Voter\AiSettingsVoter` decides `ADMIN_AI` (the changes of the Admin › AI tab) by asking `ADMIN_AREA` on the same organization through the AccessDecisionManager, so `AdminAreaVoter` alone owns the admin login rule; `UI\Voter\InvitationVoter` decides `ORG_ACCEPT_INVITATION` on an `OpenInvitationLink` (the logged-in account with the invited email, or nobody logged in when no account has that email yet). All five extend SharedKernel's `DenyByDefaultVoter`. `UI\SendAdminToTwoStepProof` turns a refused `ADMIN_AREA` of such an Admin into a redirect, through Identity's `TwoStepProofPages`: to the setup page while two-step login is off, else to "Confirm it's you". `UI\HideAdminAreaFromNonAdmins` turns a refused `ADMIN_AREA` of a logged-in person who is no Admin of the request's organization into a 404, so the admin pages do not show they exist (P14.T3); an Admin refused for another reason, such as a remember-me login, and any personal access token keep the 403, and a visitor goes to the login page. The demo seed step `Infrastructure\Demo\SeedDemoOrganizations` creates Acme Foods with its teams and Beta Bakery with Ben and his team Ovens under the step policy `team` (set with `ChangeStepPolicy` when the team is created, so Ben can try the rule switches) through these commands. `Infrastructure\Demo\FirstAdminDemoOrganizations` implements `DemoOrganizations::idBySlug`, so the demo seed steps of other modules find a demo organization by its slug (among the organizations of its first admin, each read through `OrganizationTransactions::runAs`, so it throws `TenantSwitchRefused` when a transaction is open). It may use the Api of Identity.
