# Assist

AI help that only suggests: summaries, explanations, intake suggestions and prompt packages for laptop AI. A person always clicks to apply. It owns the tables `ast_explanation`, `ast_suggestion`, `ast_embedding`, `ast_usage` and `ast_local_package`. Its Api is `AiPolicy`, `Summaries`, `Explanations`, `IntakeAssist` and `LocalAi`. It may use the Api of Ticketing, Review, Organization and Audit, and its UI the Api of Identity (time zone and names for "The ask").

## Built (phase 08, PR 1)

- **Api:** `AiPolicy` with `PolicyView` (the organization's AI policy for a person, with the one line that says why not; `serverTicketRefusalOf` gives the line that keeps the server's AI from a ticket, in the gateway's order); `Summaries` with `SummaryRequestView` and `SummaryRequestRefused` ("Summarize with AI": `request` queues a `GenerateSummary` job, `latestRequestOfVisibleTicket` reads a queued or failed request for the page that polls, after the page's own voter check).
- **Domain:** `AiFeature` (`summary`, `explain`, `intake`).
- **Application:** `AiGateway`, the one door to server AI, implemented by `Gateway\GuardedAiGateway` (policy through `Gateway\AiTaskAdmission` and `Policy\PolicyEvaluator`, the ticket through the `Gateway\AskedTicketQueries` port, limit, provider, answer check, metering); an intake task carries an `AiDraft` instead of a ticket, which the admission keeps from cloud AI when Ticketing's `DraftReportChecks` finds security words, and sends with the open duplicate candidates the reporter may see (Ticketing's `TicketVisibilities` and `IntakeCandidateQueries`; team-only ones only with the admin's opt-in), whose keys alone survive the answer check; the ports `AiProvider`, `PromptRenderer` (with `PromptVersion`), `AiAnswerCheck` (rejecting with `AiAnswerRejected`), `Metering` and `AiCallLimit` (30 calls an hour per person); `Summaries\QueuedSummaries` with the ports `SummaryRequests` and `SummaryJobQueue` and the messages `GenerateSummary` and `EndSummaryRequest`.
- **Infrastructure:** `Platform` (`SymfonyAiProvider`, the only Symfony AI user, and `FakeProvider` for tests); `Prompt` (`PromptBuilder`, `DelimitedTicketData`, `UntrustedText`, `OutputValidator` and the templates `summary.v1` and `intake.v1` with its schema); `Doctrine\DbalMetering` and the `ast_usage` partitions (`Scheduler\AddUsagePartitions`, `Scheduler\DropExpiredUsagePartitions`, `Health\NextUsagePartitionExists`); `RateLimit\SymfonyAiCallLimit`; `Messenger` (`GenerateSummaryHandler` on `async_ai`, `EndSummaryRequestHandler`, `MessengerSummaryJobQueue`); `Valkey\ValkeySummaryRequests`, the request state on the state Valkey. An answered summary is stored by Ticketing through `TicketSummaryCommands::storeAiSummary`.
- **UI:** `LocalAiChip` (who gets the header's "Local AI" chip and its sheet, and the `connect-src` to Ollama on those pages only) and `Controller\LaptopController` (`POST /ai/laptop/status`, 204, stores nothing).
- **Tables:** `ast_usage` only.

## Built (phase 08, PR 2)

- **Intake path ("Check with AI"):** the Api `IntakeAssist` with `DraftReport`, `IntakeCheckId`, `IntakeCheckView`, `IntakeSuggestion` and `IntakeCheckRefused`. `Application\IntakeAssistService` reads the requester through `AiRequesters` (shared with the summary path), refuses an over-cap draft, a non-member, what `AiTaskAdmission` refuses and a person with no call left before anything is kept, then takes a UUIDv7 of now as the check's id (`Intake\IntakeCheckIds`, `Uid\UuidV7IntakeCheckIds`) and opens the check on the state Valkey (`Intake\IntakeRequests`, `Valkey\ValkeyIntakeRequests`): the small polled state under one key, an hour while queued, and the draft under a key of its own, an hour, removed on every end path, so a poll never reads the draft. A person has at most 3 checks open per organization; a fourth is refused with "You have 3 AI checks running. Wait for one to finish." (`Intake\TooManyOpenIntakeChecks` inside, `IntakeCheckRefused::TOO_MANY_OPEN_CHECKS` outside) and nothing is kept. It queues `Intake\GenerateIntakeSuggestion` on `async_ai` (`Intake\IntakeJobQueue`, `Messenger\MessengerIntakeJobQueue`). `Messenger\GenerateIntakeSuggestionHandler` marks the check and takes its draft before the one gateway call, stores the checked answer in `ast_suggestion` (`Intake\IntakeSuggestionMapper`, `Application\Suggestions`, `Doctrine\DbalSuggestions`), and ends the check after its commit (`Intake\EndIntakeRequest`, `Messenger\EndIntakeRequestHandler`); `Messenger\FailIntakeRequestOfAbandonedJob` fails a check Messenger gave up on. Only the person who asked reads the check (`checkOf`). No `SuggestionReady` event is emitted yet: the New ticket form polls `checkOf` through `IntakeCheckController`.
- **Laptop path (summary):** the Api `LocalAi` with `LocalAiPurpose`, `PromptPackage`, `LocalPackageId`, `LocalModelName`, `LocalResult`, `LocalPackageRefused` and `LocalResultRefused`. `Application\LocalAiService` asks `Gateway\AiTaskAdmission::admitToLaptop` (not an admin with no team or manager role, whom `Policy\PolicyEvaluator::refusalForLaptopViewer` refuses for the chip too; laptop or laptop first, title only applies, a team-only ticket may go), builds the prompt with `PromptRenderer` and stores a single-use package that expires in 5 minutes (`LocalAi\LocalPackages`, `Doctrine\DbalLocalPackages`; ids from `LocalAi\LocalPackageIds`, `Uid\UuidV7LocalPackageIds`), at most 10 open and 30 issued in the last hour per person and organization, both counted under one advisory lock per person and organization. `accept` finds the package through `resolve_laptop_package`, refuses another person's or organization's as not found, a used or expired one as gone, asks `admitToLaptop` again so a policy changed since the package was issued refuses it, and refuses a model name or text that fails `LocalModelName` or `AiAnswerCheck` (or a comment's 10,000 characters) as rejected, then keeps the text on the package in one conditional `UPDATE`. It runs in a transaction of its own (`Transactions`): every refusal writes the Audit entry `local_ai.result_refused` (data `{reason, model}`, never the text) and commits it before the refusal is thrown, so the 12b result route needs `_request_transaction: false`. No `ast_usage` row and no `AiCallLimit` count, as no provider is paid. A result never becomes the current summary by itself.
- **Use as main summary (laptop result):** `LocalAi::proposalOf` reads the ticket's newest posted result not yet made main, posted after the current summary; `LocalAi::makeMainSummary` goes through `LocalAi\MainSummaryMaker` (`Doctrine\DbalMainSummaryMaker`), which marks the result made main and stores it through Ticketing's `TicketSummaryCommands::storeChosenLaptopSummary` in one savepoint, so it happens once only and nothing changes on a refusal.
- **Laptop routes (task 12b):** `UI\Controller\LaptopController` adds `POST /ai/laptop/package` (200 `{packageId, instructions, prompt, schema, expiresAt}`) and `POST /ai/laptop/result` (201 `{packageId, label, text, model, postedAt}`, without the request transaction). Both check membership (403), the `ai_laptop` form token (422), then `LaptopRequestLimit` (`RateLimit\SymfonyLaptopRequestLimit`, the limiter `ai_laptop_per_user`: 30 requests a minute per person and organization over both routes, keyed by the clock's minute, 429 with "You sent too many laptop AI requests. Wait a minute and try again." and a Retry-After, failing closed when Valkey is down), a body cap (1 KB, 120 KB; 413), the fields (422) and a malformed id (404 as an unknown one), before `LocalAi`. `UI\LaptopRefusalStatuses` maps every refusal code (ADR-0042; an unnamed code is 403).
- **UI:** `Component\TheAsk`, "The ask" on the ticket page (the summary with its source note from `SummarySourceNote`, the earlier summaries, "Summarize with AI", the laptop proposal and "Use as main summary"), served again by `Controller\SummaryController` (`GET` and `POST /t/{key}/summary`, `GET /t/{key}/summary/earlier`, `POST /t/{key}/summary/laptop/{packageId}`); `Component\IntakeCheck`, "Check with AI" on the New ticket form, served by `Controller\IntakeCheckController` (`POST /tickets/new/check`, `GET /tickets/new/check/{checkId}`); `ViewerAiPolicy`, the viewer's AI policy read once per request for the chip and both buttons. In the browser, the `summary-poll`, `intake-check` and `laptop-summary` controllers.
- **Tables:** `ast_suggestion` (`Version20261118100000`), `ast_local_package` (`Version20261118120000`; `Version20261118140000` added `result_label` and `made_main_at`, and the `laptop` source and `chosen_by_id` of Ticketing's `tkt_summary`).
