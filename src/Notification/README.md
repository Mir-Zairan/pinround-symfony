# Notification

Pings, the bell, mutes and email digests. Pings are rate limited and clear by themselves when the person acts on the ticket. It owns the tables `ntf_ping`, `ntf_notification`, `ntf_mute` and `ntf_delivery`. Its Api is `PingCommands` and `NotificationQueries`. It may use the Api of Organization and Ticketing.

Its events, in `Api\Event`, are `PingSent` and `PingCleared` (`PingEvent`, which extends `NotificationEvent`; ids only, through the outbox to `async_notify`); `Domain\QuietHours` decides whether a notification is held until 09:00.

Quiet hours: when the organization's `quiet_hours` is on, `Application\Notify\DeliveryTimes` holds any bell row (ping, question, answer, reply, assignment) made from 18:00 to 09:00 on the recipient's clock (Organization's `MemberTimeZoneQueries`; UTC for an unknown zone) by giving it a `deliver_after` at the next 09:00; the bell leaves a held row out until then. Every 5 minutes `Infrastructure\Scheduler\ReleaseHeldNotifications` finds the organizations with a row due through the resolver `organizations_with_due_notifications` (it runs with no tenant set; see the [data model](../../docs/02-architecture/data-model.md#row-level-security)) and sends each a `ReleaseDueNotifications` on `async_notify`; `ReleaseDueNotificationsHandler` releases that organization's due rows in one UPDATE and pushes each released recipient's bell once (`RefreshBell`).

The ping limit is `Application\Ping\PingWindow`: one slot per sender, recipient and ticket for the organization's `ping_limit_hours` (Organization's `PingSettingsQueries`). `Infrastructure\RateLimit\ValkeyPingWindow` keeps each slot on the state Valkey as the key `ping:<organization>:<from>:<to>:<ticket>` holding `<again at, Unix seconds>:<ping id>`, taken by one Lua script (`SET NX EX`, else the held value) so two pings at once cannot both pass. A held slot refuses with `Api\PingTooSoon` (its `againAt`); an unreachable Valkey or a failed script refuses with `Api\PingsPaused` and takes nothing, so pings stop rather than go unlimited. `release` deletes the key only while it still holds that ping's id. `heldUntilOf` reads the slots of one sender and ticket for several recipients in one `MGET` and answers when each held one ends; the ticket page's People rows (`UI\Component\PingSheet`, through `UI\PingedState`, once per request, ticket and rows) show "Pinged · again in N h" from it, so the page shows what a POST would refuse with no SQL. The sheet's note takes the ping limit through `UI\PingedState` too, once per request, in the open transaction (the ticket page renders in the request's, a move's stream answer in its re-read's), or in one of its own when none is open, as outside one row-level security shows the 4-hour default. While Valkey is down nobody is shown pinged; the POST still refuses with `PingsPaused`.

`PingCommands::ping` returns the `PingSlot` it took; when the ping's transaction fails to commit, `PingCommands::releaseSlot` gives that slot back, so a ping that was never stored does not hold the limit.

Its tables are built (`Version20261114130000`): `ntf_ping` mapped by `Domain\Ping`; `ntf_notification` (monthly partitions from `NotificationPartitions`), `ntf_mute` and `ntf_delivery` are DBAL tables hidden by the `schema_filter`. All are tenant tables with row-level security; all but `ntf_delivery` go with their ticket (ON DELETE CASCADE); see the [data model](../../docs/02-architecture/data-model.md#notification-assist-integration-audit-agentapi).
