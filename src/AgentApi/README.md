# AgentApi

The REST API under `/api/v1` and the MCP tools at `/mcp` for the browser plugin, the CLI and AI agents. These are thin adapters: each call goes to another module's Api after the same Voter check as the web UI. It owns the table `api_idempotency_key`. It has no Api of its own. It may use the Api of Identity, Ticketing, Review, Conversation, Media, Audit, Insight and Workflow.

## Depends on

- Identity Api: `CurrentApiToken::access()`, the request's `ApiTokenAccess` (token id, organization, scope names, and `expiresAt`, the token's expiry in UTC), which the stateless `api_token` firewall (`TokenAuthenticator`, security.yaml) sets for every request under `/mcp` and `/api/v1`; `CurrentUser::id()`, the token's user; `UserQueries::byIds()`, for whoami's display name.
- Audit Api: `AuditLog::record()`, for the row of each tool call. Audit's own allow-list (`Audit\Application\AuditDataAllowList`) lists `mcp.tool_called` with exactly `tool` and `outcome`, and `DbalAuditLog` refuses any other key.
- Ticketing Api: `TicketKeyQueries` (a key to a ticket id), `TicketTurnQueries::factsOf` and `TicketPermission::VIEW` (whether the caller may see the ticket), `TicketVisibilities::of` (the caller's visibility for `list_my_tickets` and `get_ticket`), `TicketQueries::pageOf` (the ticket page's read) and `TicketPageTurns::of` (the page's Now, Next and People), for `get_ticket`.
- Review Api: `RoundQueries`, `OpenDraftQueries`, `RoundCommands`, `DraftScreenshotCommands`, `ChecklistQueries`, `ChecklistCommands`, `ReportDrafts` (for `create_report` and `add_report_screenshot`), `Notebooks` (for the six notebook tools), and the voter attributes `RoundPermission`, `ChecklistPermission`, `ReportDraftPermission` and `NotebookPermission`.
- Ticketing Api, also: `ProjectQueries::projectByKey`, the project of `create_report_upload` and `create_report` (its id is their audit target).
- Conversation Api: `ThreadQueries::threadOf` and `ConversationPermission::COMMENT`, for the open questions of `get_ticket`.
- Media Api: `Uploads::begin`, `UploadBeginLimit`, `UploadCompletions`, `SignedUrls`, and `MediaPermission::UPLOAD`.
- Insight Api: `MyTicketQueries::myTicketsOf`, for `list_my_tickets`.
- Workflow Api: `StepQueries::stepsFor` and `NowNext`, for the Now line of `list_my_tickets`.

## What it has now

- The MCP server (ADR-0021, P09.T2): `symfony/mcp-bundle` pinned to exactly 0.15.0, on `mcp/sdk` 0.9 (config/packages/mcp.yaml). The server key is `pinround` (its `serverInfo.name`), and its route `_mcp_endpoint_pinround` answers GET, POST, DELETE and OPTIONS at `/mcp` (config/routes/mcp.yaml).
  - The registry is `'*'`: the tools are `AgentTool`s, not `#[McpTool]` services, and the bundle refuses a namespace pattern that matches no `#[McpTool]` service. A vendor `#[McpTool]` could show in `tools/list` but never run, as `GatedToolCallHandler` knows only the `AgentTool`s.
  - Sessions (`Mcp-Session-Id`) live in the pool `cache.mcp_sessions` on the state Valkey, which never evicts (ADR-0010) and which every app container shares; the test env keeps them there too. The session lock is off, so two requests of one session at once can overwrite each other's session write; turn on `session.lock` with a `LockFactory` before a tool keeps state in the session. A session carries protocol state only: every request still authenticates by its own Bearer token, and `McpSessionBinding` (below) keeps a session to the token that started it.
  - The SDK has its own checks behind ours: a 4 MB body cap, and a DNS rebinding check whose allowed host is DEFAULT_URI's (`allowed_hosts`). It also lets an `Origin` through only when it equals the request's own scheme and host, so a request must reach PHP with the public scheme (behind a TLS proxy, through trusted proxies).
- `Infrastructure\Mcp\McpRequestGuard`, on every main request under `/mcp`, in this order:
  1. Before the firewall, so no token is looked up for a refused request: a Host other than DEFAULT_URI's gets 400 (`UNKNOWN_HOST`), an `Origin` other than DEFAULT_URI's origin 403 (`FOREIGN_ORIGIN`), and a body over 1 MB 413 (`BODY_TOO_LARGE`; a Content-Length over the cap is refused unread, a body without one is read to one byte past the cap).
  2. The firewall: a missing, revoked, expired or unknown token, and a browser session cookie alone, get 401.
  3. After `EnterChosenOrganization` and the request transaction's BEGIN: `ToolCallLimiter` spends one call, and a spent limit gets 429 with `Retry-After` in seconds to the end of the clock's minute or hour.
  4. `Infrastructure\Mcp\McpSessionBinding` (priority 4, after the limits, before the MCP controller): a request with `Mcp-Session-Id` whose session is bound to another token or organization, or to none (unknown, expired, not a UUID, the header sent twice), gets 404 with the SDK's own JSON-RPC error "Session not found or has expired." (`-32600`), so another token's session looks like a missing one, and no tool runs. The response to a request without `Mcp-Session-Id` that carries a new one (initialize) binds that session to the token id and organization id, in `cache.mcp_sessions` under `mcp_session_binding.<uuid>` (RFC 4122 form, as the SDK reads every spelling of a UUID as one session) for `TTL_SECONDS` (3600, equal to `session.ttl` in mcp.yaml, which `McpServerConfigTest` pins). Each passed request refreshes the TTL; an SDK 404, or a DELETE the SDK answered 2xx, forgets the binding. A request without `Mcp-Session-Id` passes on to the SDK, which starts a session only for initialize.
- `Infrastructure\Mcp\ToolCallLimiter` (rate_limiter.yaml): per token 60 calls a minute and 600 an hour, per organization 600 a minute (`TOKEN_TOO_FAST`, `TOKEN_HOUR_SPENT`, `ORGANIZATION_TOO_FAST`). Each counter is keyed by the clock's minute or hour, on the state Valkey; a counter that cannot be read or written fails the call. A refused call spends nothing of the limits after the one that refused it.
- The gate and the tools (P09.T2 to P09.T5). The gate's classes are in `Infrastructure\Mcp`, each tool in `Infrastructure\Mcp\Tool`:
  - `AgentTool`, the contract of a tool (tagged `agent_api.tool`): its definition (name, description, input schema), the scope it needs, `targetOf()` (a `ToolTarget`: the voter attribute and subject the web UI checks, and the audit target) and `call()`. A tool may throw a `ToolRefusal`: not found, read-only, invalid input, or `refused` (a plain reason of the domain the caller can act on, such as a rejected picture). The gate's savepoint takes back anything the tool wrote before it threw.
  - `AgentToolLoader` (an SDK loader) lists each tool in `tools/list`, a `ScreenshotContextRequiredOverMcp` tool by its `mcpDefinition()`; the registry's own handler for a tool only throws.
  - `GatedToolCallHandler` (an SDK request handler, asked before the SDK's `CallToolHandler`) answers every `tools/call`. An unknown tool name gets a JSON-RPC invalid-params error and no audit row.
  - `ToolCallGate` runs each call: the token's scope, the input schema (a new SDK `SchemaValidator` per call, which logs nothing), `targetOf()`, the voter (a denial is "not found", ADR-0013), `call()`. Over MCP `GatedToolCallHandler` uses `callOverMcp()`: for a `ScreenshotContextRequiredOverMcp` tool (`create_report`, `add_screenshot`, `add_notebook_screenshot`, `add_report_screenshot`, P14.T11) it runs `refuseMissingScreenshotContext()` after the scope check and then checks `mcpDefinition()`'s schema, which requires each picture's title and summary, so a missing, empty or blank one (only white space, control or format characters, such as CR LF or a BOM) is invalid input, `ScreenshotContextArguments::MISSING_OR_BLANK` naming its JSON pointer (`/summary`, `/screenshots/1/title`), with one `invalid_input` audit row and no upload completed; `/api/v1` uses `call()` and `definition()`, where both stay optional (proof: `ScreenshotContextArgumentsTest` and `ToolCallGateTest`, unit, and `aPictureWithoutATitleOrSummaryIsInvalidInput…` in the functional `Tool\AddScreenshotTest`, `Tool\CreateReportTest`, `Tool\AddNotebookScreenshotTest` and `Tool\AddReportScreenshotTest`). A missing scope, a not-found, a read-only or a `refused` refusal is a tool error result with the `ToolRefusal` message; invalid input, from the schema or from the tool, is a JSON-RPC invalid-params error; any other failure is the generic `TOOL_FAILED` result, logged with the tool name (key `mcp_tool`, which `RedactionProcessor` allows) and the exception class only.
  - The target, the voter, `call()` and the "ok" audit row run in a DBAL savepoint of the request transaction (the gate refuses to run a tool when none is open). Any refusal or failure in it, the ok row's own write included, rolls back to the savepoint before the refusal or "error" row is written, so a call that did not end "ok" keeps only its audit row, and a tool write is never committed without its row. A tool that leaves a transaction of its own open is rolled back too and fails; one that ends the request transaction, or a rollback that fails, gets the connection closed, so the request commits nothing (a 500 at its commit). The savepoint covers DBAL writes only: a tool that uses the ORM must flush inside `call()`, as entities left unflushed are not undone.
  - `ToolCallAuditor` writes one `aud_event` per call that reached the gate, refused or not: actor kind `token` with the token id and its user, action `mcp.tool_called`, the target (or type `mcp_tool` and no id), and data exactly `tool` and `outcome` (`ok`, `not_found`, `read_only`, `missing_scope`, `invalid_input`, `refused`, `error`; `ToolCallOutcome`). Never the input, the output or the token.
  - `OwnIdentityTool`, the marker of a tool that names no target and reads only the caller's own data: their identity, their own list filtered by their own ticket visibility predicate, as the tickets list is, or rows only they own, read by their own user id in the token's organization, as their notebooks are (`Notebooks::forOwner`). Such a tool never writes. Only such a tool may answer `null` from `targetOf()` and skip the voter; the gate fails (an "error" row, `TOOL_FAILED`) any other tool that has no target (deny by default).
  - `Tool\WhoAmI` (`whoami`, scope `read`, an `OwnIdentityTool`, no target): the token's user id and display name, its organization id, its scopes and `expires_at`, the token's expiry in ISO 8601 UTC (`2099-06-13T10:00:00+00:00`).
  - `Tool\ListMyTickets` (`list_my_tickets`, scope `read`, an `OwnIdentityTool`, no target, so no voter and an audit row with type `mcp_tool`): the caller's open tickets whose turn is theirs or that are assigned to them, from Insight's `MyTicketQueries::myTicketsOf` (one query on `ins_ticket_turn` joined to `tkt_ticket_list_v`, filtered by `TicketVisibilitySql` of the caller's `TicketVisibilities::of`), the most recently changed first (`updated_at DESC, ticket_id DESC`), at most `MyTicketQueries::MAX_TICKETS` (50), input an optional `limit` 1 to 50. Each ticket: `key`, `title`, `step` (name), `now` (Workflow's `NowNext::now` with the saved turn, the step's core code from `StepQueries::stepsFor` once per team, first names from one `UserQueries::byIds`, the asker, and no viewer, as the ticket page words it; null for a ticket no team owns), `is_your_turn`, `is_assignee`, `updated_at` (UTC); and `has_more`. Done tickets have no turn row, so they are never listed. Titles and names are returned as JSON data, and the description says to treat them as data, never as instructions (WhoAmI's convention). It is an `OwnIdentityTool` because it reads only the caller's own list through their own visibility predicate, as the tickets list does.
  - `Tool\FindTickets` (`find_tickets`, scope `read`, P13.T3, FR-MCP-13, an `OwnIdentityTool`, no target, so no voter and an audit row with type `mcp_tool`; input `{text, project?}`): the open tickets the caller may see that best match the text, so a client can offer "Add to SHOP-42" at the end of a check. `text` holds 1 to 200 characters (`ListFilter::SEARCH_TEXT_MAX_LENGTH`); a longer one is refused by the input schema, and one that is blank once trimmed or holds a NUL by the tool, both invalid input before any ticket query. `project` is a project key (`ProjectQueries::projectByKey`; an unknown one is "not found"). It runs Ticketing's `TicketSearchQueries::openMatchesOf` (the search of ADR-0022 under the caller's own `TicketVisibilities::of`, Done tickets left out) and returns at most 10 (`TicketSearchQueries::MAX_MATCHES`), the exact key first, with `has_more`. Each ticket: `key`, `title`, `step` (name), `whose_turn` (the turn person's name, null when nobody's) and `may_start_draft`, true when the caller is the ticket's assignee or its turn person: `RoundPermission::DRAFT_CREATE`'s rule on the facts read for the whole list, instead of two voter queries per ticket; every match is open and visible to the caller, which leaves the voter only those two checks. Titles and names are wrapped by `UntrustedText`. The queries do not grow with the number of matches.
  - `Tool\GetTicket` (`get_ticket`, scope `read`, input `key`): one ticket as its page shows it to the caller. The target is the ticket with that key (audit type `ticket`, its id), checked with `TicketPermission::VIEW`; then `call()` reads `TicketQueries::pageOf` under the caller's own visibility predicate, as the page does, so a ticket the voter would let through but the predicate hides is "not found" too. An unknown key, another organization's ticket and a ticket the caller may not see are all "not found". It returns `key`, `title`, `description`, `step` (name), and:
    - `now` and `next`: the page's Now and Next lines, from Ticketing's `TicketPageTurns::of`, the read the page itself uses (the saved turn from Insight, or `TurnRules`' turn for a ticket with none, worded by Workflow's `NowNext` with first names and no viewer); both null for a ticket no team owns, `next` null when nothing comes next. `GetTicketTest` compares them with `/t/SHOP-1`'s lines for a saved answer turn.
    - `people`: the People section, from the same `TicketPageTurns::of` (the assignee, the reporter, the code reviewer while In progress or in Code review, the tester while the ticket is open; a reviewer or tester not stored yet is the one the team would pick). Each person once, with `name` and every role they have (`assignee`, `reporter`, `reviewer`, `tester`, Ticketing's `TicketRole`); the page shows "reporter" only when the person has no other role. A name Identity does not know is null. `GetTicketTest` compares them with the page's People rows on a Code review ticket.
    - `open_questions`: the open questions among the newest messages the thread shows, oldest first (`question_id`, `text`, `asked_by`, `asked_to`, `asked_at` in UTC); answered and removed ones never. Null, never `[]`, when `ConversationPermission::COMMENT` denies the thread.
    - `checklist`: `ChecklistQueries::forTicket` in `get_round_notes`' shape (`Infrastructure\Mcp\ChecklistFields::of`, which both tools use), null when there is none or `RoundPermission::VIEW` denies its round.
    - Titles, descriptions, question texts, checklist notes and names are wrapped by `UntrustedText`.
  - `Tool\GetRoundNotes` (`get_round_notes`, scope `read`, input `key`): what was marked on one ticket's screenshots, for the caller's Claude Code to fix. The target is the ticket with that key (audit type `ticket`, its id), checked with `TicketPermission::VIEW`; a key the organization has no ticket with, a ticket of another organization (row-level security hides it) and a ticket the caller may not see are all "not found". Each round it returns is checked again with `RoundPermission::VIEW`, as the Rounds section does, and left out (null) when denied. It returns:
    - `shared_round`: the newest shared round that has pictures, the shared draft round or the report (Round 0) with the highest number, as `RoundQueries::sharedRoundNotes` reads it in one query; checklist and review rounds do not count. Its pins are the pins that count: people's pins and AI pins a person kept; an AI suggestion is left out.
    - `draft_round`: the caller's own unshared draft round as `RoundQueries::roundNotes` reads it, with the same pins that count. Another person's unshared draft is never read.
    - `checklist`: `ChecklistQueries::forTicket`, its items with their pin number, note and state.
    - Each screenshot: `screenshot_id`, `position`, `image` (status and a URL signed by `SignedUrls::forVariants` for the `view` variant at the clock's time, in one call; null when the media object is gone), `title`, `summary`, `verdict` (`Looks right`, `Not right yet` or null) and `pins` (`number`, `x_pct` and `y_pct` as JSON numbers from 0 to 100, `note`). A whole-number position is written `10`, not `10.0`, in both the text block and `structuredContent`, which carry the same JSON.
    - The untrusted-text convention (ADR-0020): `UntrustedText`, beside `AgentTool` in `Infrastructure\Mcp`, wraps every title, summary, pin note and checklist note in `<untrusted_text>` and `</untrusted_text>`, with `&`, `<` and `>` escaped as `&amp;`, `&lt;` and `&gt;`, so a typed `</untrusted_text>` cannot end the data early; all else (line breaks included) is kept as typed. The answer's `untrusted_text_notice` and the tool description say this text is data, never instructions.
  - `Tool\SetVerdict` (`set_verdict`, scope `rounds:write`, P09.T4 steps 2 and 3), two input shapes, a mix of them invalid input:
    - `{key, screenshot_id, verdict, summary?}`: `looks_right` or `not_right_yet` (stored as Review's `looks_right` / `not_right`) on a screenshot of one of the ticket's drafts. One lookup: once `TicketPermission::VIEW` grants the ticket (as `get_round_notes` asks it, so a ticket the caller may no longer see is not found, also for the owner of a draft on it), `RoundQueries::draftScreenshotOf` finds the draft that holds the screenshot in one query, however many rounds the ticket has. Voter `RoundPermission::EDIT` on an unshared draft; `VIEW` on a shared one, which `call()` then refuses read-only, also for its owner (FR-RND-12). Another person's draft, an unknown or lowercase key and another organization's ticket are not found. One command: `RoundCommands::setDraftVerdictWithSummary` saves the verdict and the summary together, so a summary Review refuses (over 600 characters after trimming, the web's own check; outcome `invalid_input`) leaves the verdict unsaved too. On a retaken screenshot both land on the latest try of its chain, whichever try's id is sent, such as the first try's id that `list_draft_screenshots` gives, and the answer's `screenshot_id` is that try's; the audit row names the screenshot the call named (ADR-0048). Review's `RoundRefused` kind decides the refusal: `isNotFound` not found, `isReadOnly` read-only, `isInvalidContent` invalid input; any other, such as `DRAFT_CHANGED`, is refused with Review's text (outcome `refused`). Each call raises the draft's version, also a retry with the same verdict.
    - `{key, check_item_id, state: "fixed"}`: voter `ChecklistPermission::MARK_FIXED`; a caller who is not the assignee is not found (the gate answers every denial so; the web's card answers 403), an item marked fixed already or confirmed OK read-only.
    - The schema has no top-level `oneOf`/`anyOf`, which Claude's tool input schema refuses there: `dependentRequired`, `dependentSchemas` and `minProperties` (JSON Schema 2020-12) carry the two shapes. Audit target `screenshot` or `check_item`.
  - `Tool\CreateUpload` (`create_upload`, scope `rounds:write`, P09.T5, input `{key, mime, bytes, sha256}`): begins a direct upload of one screenshot into the caller's own open unshared draft round of the ticket, and answers `upload_id`, `put_url`, `headers` and `expires_at`. The picture never passes through PHP (ADR-0011).
    - `targetOf()` reads the caller's draft with Review's `OpenDraftQueries::openDraftOf`, which never returns another person's draft or a shared one. With a draft: the ticket must pass `TicketPermission::VIEW`, then the voter is `MediaPermission::UPLOAD` on the draft (audit target `round`). Without one: the voter is `RoundPermission::DRAFT_CREATE` on the ticket, which grants its assignee and the person whose turn it is (ADR-0044; audit target `ticket`), and `call()` starts the draft with `RoundCommands::startDraft` and asks `MediaPermission::UPLOAD` on it.
    - `call()` first spends one of the caller's begins with Media's `UploadBeginLimit`, shared with the web's `POST /media/intents`; past it the call is refused with Media's message ("You are adding files too fast. Wait a minute and try again."). Then `Uploads::begin` runs with the web's own checks: a wrong type or size, a twenty-first upload waiting or a full storage is refused with Media's plain message. The gate's savepoint takes a new draft back when the begin is refused.
    - The `sha256` is checked for its form only: the PUT URL pins the type and the exact size, not the checksum.
  - `Tool\AddScreenshot` (`add_screenshot`, scope `rounds:write`, P09.T5, input `{key, upload_id, title, summary, pins?: [{x_pct, y_pct, note}]}` over MCP, `title?, summary?` over `/api/v1`): puts a picture uploaded through `create_upload` into the caller's own unshared draft round, with its title, summary and pins (FR-RND-16).
    - `targetOf()` first asks `TicketPermission::VIEW` on the ticket, so a ticket the caller may no longer see is not found, also for the draft's owner, and the upload stays unused. Then it reads what the upload was begun for with Media's `UploadCompletions::targetOf`, which answers only an upload the caller began in the token's organization. An upload not begun for a round (`DraftScreenshotCommands::UPLOAD_TARGET_KIND`) or for a round of another ticket is not found. The voter is `RoundPermission::EDIT` on an unshared draft, `VIEW` on any other round, which `call()` then refuses read-only (audit target `round`).
    - `call()` finishes the upload with `UploadCompletions::completeInTransaction` in the gate's savepoint. The picture's id is the upload's id on every path, so the same `upload_id` finds the same picture on every call.
    - A picture still processing is an "ok" answer with `status` `processing`, not a refusal: the completion is kept, and the next call with the same `upload_id` finds it. A rejected picture is refused (outcome `refused`), and so is an upload that expired unused.
    - A ready picture goes in through `DraftScreenshotCommands::addDraftScreenshotOnce`. A picture the draft holds already is answered `added_before` with its `screenshot_id`, and nothing is saved, so a retry never adds a second screenshot; the title, summary and pins of that call are not used. Review's refusals map by kind as in `set_verdict`; one of no kind, such as `DRAFT_CHANGED`, is refused with Review's text (outcome `refused`).
  - `Tool\ListDraftScreenshots` (`list_draft_screenshots`, scope `read`, P14.T6 step 4, input `{key}`): the screenshots of the caller's own open unshared draft round on the ticket, so a client can offer "Retake of screenshot N" and send that screenshot's `screenshot_id` as `add_screenshot`'s `retake_of`. It answers `{untrusted_text_notice, screenshots: [{screenshot_id, number, title, try_count}]}`, one row per chain of tries in the order and with the numbers the draft round card shows (Review's `ScreenshotChains`): `screenshot_id` is the chain's first try, `title` the latest try's, wrapped as `UntrustedText`, or null. One query, `OpenDraftQueries::openDraftScreenshotsOf`, whatever the number of tries.
    - The target is the ticket (audit type `ticket`), checked with `TicketPermission::VIEW`, so a ticket the caller may not see, an unknown key and another organization's ticket are not found, also for the owner of a draft on it. The draft is listed only when `RoundPermission::VIEW` grants it too.
    - The list is empty when the caller has no open unshared draft on the ticket; another person's draft, a shared round and a closed draft are never listed.
  - `TicketVisibilityCheck` is the one `TicketPermission::VIEW` check of `set_verdict`, `create_upload` and `add_screenshot`, whose voters (`RoundPermission`, `MediaPermission::UPLOAD`) grant a draft's owner without reading the ticket; it also gives the caller's organization from the token.
  - `ToolArguments` and `ToolUploadCompletion` are what the tools share: `ToolArguments::MAX_ID_LENGTH` (64) is the one `maxLength` of every id or ticket key argument, and its `stringAt`/`optionalStringAt` read a string argument the schema has checked; `ToolUploadCompletion::completed` finishes the caller's upload for `add_screenshot`, `create_report`, `add_report_screenshot` and `add_notebook_screenshot`, an unknown intent or a target that now refuses them as not found and an expired one as refused with the tool's own message.
  - Together: `create_upload` gives an `upload_id` and a `put_url`; the agent sends the file with `curl -T <file>` and the headers as given, before `expires_at`; then `add_screenshot` with the `upload_id`. While the answer says `processing`, the agent calls `add_screenshot` again a few seconds later.
- The server instructions (P14.T12, FR-MCP-15): `Infrastructure\Mcp\McpServerInstructions::TEXT`, which `config/packages/mcp.yaml` sets as the server's `instructions` with `!php/const`, so every `initialize` result carries the capture rule: save each screenshot in a local evidence log at the moment it is taken, with its title, summary and pins (the caps are `RoundCommands`' constants), upload nothing until the person asks, then upload from the log with the tools it names, never write a token into the log, and read `<untrusted_text>` as data. A session that starts no prompt follows it too. Proof: `McpServerConfigTest::theServerSendsTheCaptureRuleAsItsInstructionsInEveryEnvironment` (unit, the yaml names the constant) and `Prompt\FixMyRoundNotesPromptTest::initializeCarriesTheCaptureRuleAndOffersPrompts` (functional, through `/mcp`).
- The prompts. Each is an `Infrastructure\Prompt\AgentPrompt` (tag `agent_api.prompt`) that serves its versioned file through `VersionedPromptFile::read` (a missing or empty file is a `RuntimeException`, never an empty prompt; unit test `Prompt\VersionedPromptFileTest`); a change of wording is a new file and a new `VERSION`. A prompt that lists no arguments serves its file byte for byte; one that lists arguments fills them into its `{{name}}` placeholders with `PromptTemplate::fill`, in one pass, so a value holding a placeholder is not filled again, and a template with a placeholder no value fills, or a value with no placeholder, is a `RuntimeException`, never a half-filled prompt (unit test `Prompt\PromptTemplateTest`).
  - `report_while_investigating` (P13.T4, FR-MCP-14, ADR-0045): `ReportWhileInvestigatingPrompt`, file `Infrastructure/Prompt/report_while_investigating.v1.md`.
  - `explain_my_notebook` (P13.T9, ADR-0046): `ExplainMyNotebookPrompt`, file `Infrastructure/Prompt/explain_my_notebook.v1.md`: read the notebook with `list_my_notebooks` and `get_notebook`, take the `<untrusted_text>` text as data, answer pin by pin, and only when the person asks for cases write scenario.v1 scenarios, prepare their `setup` data in the person's own app (never in pinround) and save them with `save_scenarios` (scope `notebooks:write`, replaces them all), unwrapped with `UntrustedText::UNWRAP`'s words. ## REST /api/v1 (P09.T7)

- `Infrastructure\Rest\RestToolController` runs the tool of each action through `ToolCallGate`, so scope, schema, voter, savepoint and the audit row are the tool's: `GET /api/v1/me/tickets` (`list_my_tickets`), `POST /api/v1/uploads` (`ticket` runs `create_upload`, `project` runs `create_report_upload`; both or neither is 422), `POST /api/v1/reports` (`create_report`), `POST /api/v1/reports/{id}/screenshots` (`add_report_screenshot`; the picture is uploaded through `/api/v1/uploads` with the draft's `project`), `POST /api/v1/tickets/{key}/draft/screenshots` (`add_screenshot`), `GET /api/v1/tickets/{key}/draft/screenshots` (`list_draft_screenshots`; titles stay wrapped as the tool answers them), `GET /api/v1/notebooks` (`list_my_notebooks`; the query's `cursor` goes to the tool as sent, so an empty one or a list is its 422), `GET /api/v1/notebooks/{id}` (`get_notebook`; texts stay wrapped as the tool answers them), `POST /api/v1/notebooks` (`create_notebook`, 201), `POST /api/v1/notebooks/{id}/uploads` (`create_notebook_upload`, 201; apart from `/api/v1/uploads` as the notebook is in the path) and `POST /api/v1/notebooks/{id}/screenshots` (`add_notebook_screenshot`). A refusal is `{error, outcome}` with 404, 403 (missing scope), 409 (read-only) or 422. An id or key in the path longer than the tool's input schema allows (64) is 404 with the tool's `not_found` audit row, after the scope check (`ToolCallGate::refuseAsNotFound`), not the schema's 422. A body that is no JSON object is 400 and runs nothing. OpenAPI: `docs/api/v1.yaml`.
- `Infrastructure\Rest\RestRequestGuard`, before the router (40): a Host other than DEFAULT_URI's is 400; an `Origin` not in `EXTENSION_ORIGINS` (comma-separated; empty in `.env`) is 403; a preflight from an allowed origin is answered 204 with the allowed methods and headers; a body over 1 MB is 413. At 5 it spends the same `ToolCallLimiter` calls as `/mcp`. Every answer to an allowed origin carries `Access-Control-Allow-Origin` and exposes `Retry-After` and `Idempotent-Replayed`.
- `Infrastructure\Rest\IdempotencyKeys` on `api_idempotency_key` (`Version20261119200000`, RLS; `pinround_app` SELECT, INSERT, UPDATE): a POST with `Idempotency-Key` reserves it per token before running (`INSERT … ON CONFLICT DO NOTHING`, so a second request with the key waits for the first), then stores the status and the exact JSON text in the same transaction. The same request again gets those bytes with `Idempotent-Replayed: true`; another request with the key gets 422. No purge yet (24 hours, with the retention job).
