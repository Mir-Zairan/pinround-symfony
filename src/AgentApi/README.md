# AgentApi

The REST API under `/api/v1` and the MCP tools at `/mcp` for the browser plugin, the CLI and AI agents. These are thin adapters: each call goes to another module's Api after the same Voter check as the web UI. It owns the table `api_idempotency_key`. It has no Api of its own. It may use the Api of Identity, Ticketing, Review, Conversation, Media, Audit, Insight and Workflow.

## Depends on

- Identity Api: `CurrentApiToken::access()`, the request's `ApiTokenAccess` (token id, organization, scope names, and `expiresAt`, the token's expiry in UTC), which the stateless `api_token` firewall (`TokenAuthenticator`, security.yaml) sets for every request under `/mcp` and `/api/v1`; `CurrentUser::id()`, the token's user; `UserQueries::byIds()`, for whoami's display name.
- Audit Api: `AuditLog::record()`, for the row of each tool call. Audit's own allow-list (`Audit\Application\AuditDataAllowList`) lists `mcp.tool_called` with exactly `tool` and `outcome`, and `DbalAuditLog` refuses any other key.

## What it has now

- The MCP server (ADR-0021, P09.T2): `symfony/mcp-bundle` pinned to exactly 0.15.0, on `mcp/sdk` 0.9 (config/packages/mcp.yaml). The server key is `pinround` (its `serverInfo.name`), and its route `_mcp_endpoint_pinround` answers GET, POST, DELETE and OPTIONS at `/mcp` (config/routes/mcp.yaml).
  - The registry is `'*'`: the tools are `AgentTool`s, not `#[McpTool]` services, and the bundle refuses a namespace pattern that matches no `#[McpTool]` service. A vendor `#[McpTool]` could show in `tools/list` but never run, as `GatedToolCallHandler` knows only the `AgentTool`s.
  - Sessions (`Mcp-Session-Id`) live in the pool `cache.mcp_sessions` on the state Valkey, which never evicts (ADR-0010) and which every app container shares; the test env keeps them there too. The session lock is off, so two requests of one session at once can overwrite each other's session write; turn on `session.lock` with a `LockFactory` before a tool keeps state in the session. A session carries protocol state only: every request still authenticates by its own Bearer token, and `McpSessionBinding` (below) keeps a session to the token that started it.
  - The SDK has its own checks behind ours: a 4 MB body cap, and a DNS rebinding check whose allowed host is DEFAULT_URI's (`allowed_hosts`). It also lets an `Origin` through only when it equals the request's own scheme and host, so a request must reach PHP with the public scheme (behind a TLS proxy, through trusted proxies).
- `Infrastructure\Mcp\McpRequestGuard`, on every main request under `/mcp`, in this order:
  1. Before the firewall, so no token is looked up for a refused request: a Host other than DEFAULT_URI's gets 400 (`UNKNOWN_HOST`), an `Origin` other than DEFAULT_URI's origin 403 (`FOREIGN_ORIGIN`), and a body over 1 MB 413 (`BODY_TOO_LARGE`; a Content-Length over the cap is refused unread, a body without one is read to one byte past the cap).
  2. The firewall: a missing, revoked, expired or unknown token, and a browser session cookie alone, get 401.
  3. After `EnterChosenOrganization` and the request transaction's BEGIN: `ToolCallLimiter` spends one call, and a spent limit gets 429 with `Retry-After` in seconds to the end of the clock's minute or hour.
  4. `Infrastructure\Mcp\McpSessionBinding` (priority 4, after the limits, before the MCP controller): a request with `Mcp-Session-Id` whose session is bound to another token or organization, or to none (unknown, expired, not a UUID, the header sent twice), gets 404 with the SDK's own JSON-RPC error "Session not found or has expired." (`-32600`), so another token's session looks like a missing one, and no tool runs. The response to a request without `Mcp-Session-Id` that carries a new one (initialize) binds that session to the token id and organization id, in `cache.mcp_sessions` under `mcp_session_binding.<uuid>` (RFC 4122 form, as the SDK reads every spelling of a UUID as one session) for `TTL_SECONDS` (3600, equal to `session.ttl` in mcp.yaml, which `McpServerConfigTest` pins). Each passed request refreshes the TTL; an SDK 404, or a DELETE the SDK answered 2xx, forgets the binding. A request without `Mcp-Session-Id` passes on to the SDK, which starts a session only for initialize.
- `Infrastructure\Mcp\ToolCallLimiter` (rate_limiter.yaml): per token 60 calls a minute and 600 an hour, per organization 600 a minute (`TOKEN_TOO_FAST`, `TOKEN_HOUR_SPENT`, `ORGANIZATION_TOO_FAST`). Each counter is keyed by the clock's minute or hour, on the state Valkey; a counter that cannot be read or written fails the call. A refused call spends nothing of the limits after the one that refused it.
- The tools (P09.T2 steps 3 to 5), all in `Infrastructure\Mcp`:
  - `AgentTool`, the contract of a tool (tagged `agent_api.tool`): its definition (name, description, input schema), the scope it needs, `targetOf()` (a `ToolTarget`: the voter attribute and subject the web UI checks, and the audit target) and `call()`. A tool may throw a `ToolRefusal` (not found, read-only) before it writes anything.
  - `AgentToolLoader` (an SDK loader) lists each tool in `tools/list`; the registry's own handler for a tool only throws.
  - `GatedToolCallHandler` (an SDK request handler, asked before the SDK's `CallToolHandler`) answers every `tools/call`. An unknown tool name gets a JSON-RPC invalid-params error and no audit row.
  - `ToolCallGate` runs each call: the token's scope, the input schema (a new SDK `SchemaValidator` per call, which logs nothing), `targetOf()`, the voter (a denial is "not found", ADR-0013), `call()`. A missing scope, a not-found or a read-only refusal is a tool error result with the `ToolRefusal` message; invalid input is a JSON-RPC invalid-params error; any other failure is the generic `TOOL_FAILED` result, logged with the tool name (key `mcp_tool`, which `RedactionProcessor` allows) and the exception class only.
  - The target, the voter, `call()` and the "ok" audit row run in a DBAL savepoint of the request transaction (the gate refuses to run a tool when none is open). Any refusal or failure in it, the ok row's own write included, rolls back to the savepoint before the refusal or "error" row is written, so a call that did not end "ok" keeps only its audit row, and a tool write is never committed without its row. A tool that leaves a transaction of its own open is rolled back too and fails; one that ends the request transaction, or a rollback that fails, gets the connection closed, so the request commits nothing (a 500 at its commit). The savepoint covers DBAL writes only: a tool that uses the ORM must flush inside `call()`, as entities left unflushed are not undone.
  - `ToolCallAuditor` writes one `aud_event` per call that reached the gate, refused or not: actor kind `token` with the token id and its user, action `mcp.tool_called`, the target (or type `mcp_tool` and no id), and data exactly `tool` and `outcome` (`ok`, `not_found`, `read_only`, `missing_scope`, `invalid_input`, `error`). Never the input, the output or the token.
  - `OwnIdentityTool`, the marker of a tool that reads only the caller's own identity: only such a tool may answer `null` from `targetOf()` and skip the voter; the gate fails (an "error" row, `TOOL_FAILED`) any other tool that has no target (deny by default).
  - `Tool\WhoAmI` (`whoami`, scope `read`, an `OwnIdentityTool`, no target): the token's user id and display name, its organization id, its scopes and `expires_at`, the token's expiry in ISO 8601 UTC (`2099-06-13T10:00:00+00:00`).
  - `Tool\ListMyTickets` (`list_my_tickets`, scope `read`, an `OwnIdentityTool`, no target, so no voter and an audit row with type `mcp_tool`): the caller's open tickets whose turn is theirs or that are assigned to them, from Insight's `MyTicketQueries::myTicketsOf` (one query on `ins_ticket_turn` joined to `tkt_ticket_list_v`, filtered by `TicketVisibilitySql` of the caller's `TicketVisibilities::of`), the most recently changed first (`updated_at DESC, ticket_id DESC`), at most `MyTicketQueries::MAX_TICKETS` (50), input an optional `limit` 1 to 50. Each ticket: `key`, `title`, `step` (name), `now` (Workflow's `NowNext::now` with the saved turn, the step's core code from `StepQueries::stepsFor` once per team, first names from one `UserQueries::byIds`, the asker, and no viewer, as the ticket page words it; null for a ticket no team owns), `is_your_turn`, `is_assignee`, `updated_at` (UTC); and `has_more`. Done tickets have no turn row, so they are never listed. Titles and names are returned as JSON data, and the description says to treat them as data, never as instructions (WhoAmI's convention). It is an `OwnIdentityTool` because it reads only the caller's own list through their own visibility predicate, as the tickets list does; `OwnIdentityTool`'s docblock still says "own identity" only.
  - `Tool\GetRoundNotes` (`get_round_notes`, scope `read`, input `key`): what was marked on one ticket's screenshots, for the caller's Claude Code to fix. The target is the ticket with that key (audit type `ticket`, its id), checked with `TicketPermission::VIEW`; a key the organization has no ticket with, a ticket of another organization (row-level security hides it) and a ticket the caller may not see are all "not found". Each round it returns is checked again with `RoundPermission::VIEW`, as the Rounds section does, and left out (null) when denied. It returns:
    - `shared_round`: the newest shared round that has pictures, which is the shared draft round or the report (Round 0) with the highest number in `RoundQueries::forTicket`; checklist and review rounds do not count. Its pins are people's pins and AI pins a person kept; an AI suggestion is left out.
    - `draft_round`: the caller's own unshared draft round exactly as `RoundQueries::roundNotes` reads it (the draft editor's read). Another person's unshared draft is never read.
    - `checklist`: `ChecklistQueries::forTicket`, its items with their pin number, note and state.
    - Each screenshot: `screenshot_id`, `position`, `image` (status and a URL signed by `SignedUrls::forVariants` for the `view` variant at the clock's time, in one call; null when the media object is gone), `title`, `summary`, `verdict` (`Looks right`, `Not right yet` or null) and `pins` (`number`, `x_pct` and `y_pct` as JSON numbers from 0 to 100, `note`). A whole-number position is written `10`, not `10.0`, in both the text block and `structuredContent`, which carry the same JSON.
    - The untrusted-text convention (ADR-0020): `Tool\UntrustedText` wraps every title, summary and note in `<untrusted_text>` and `</untrusted_text>`, with `&`, `<` and `>` escaped as `&amp;`, `&lt;` and `&gt;`, so a typed `</untrusted_text>` cannot end the data early; all else (line breaks included) is kept as typed. The answer's `untrusted_text_notice` and the tool description say this text is data, never instructions.
- Proof: `McpEndpointTest` (functional: the handshake, each refusal with its reason and the token and counters unchanged, both limits, `tools/list` and `whoami` through the real endpoint, a session used with another token of the same user or of another organization or never started gets 404 with no tool run and no audit row, and the binding's TTL in Valkey refreshed by a call), `McpRequestGuardTest`, `McpSessionBindingTest`, `ToolCallLimiterTest`, `ToolCallGateTest`, `GatedToolCallHandlerTest`, `ToolCallAuditorTest` and `AgentToolLoaderTest` (unit); `Tool\GetRoundNotesTest` (functional, through `/mcp`, and unit) and `Tool\UntrustedTextTest` (unit).

Not built yet: the organization name in `whoami` (Organization has no Api for it), the other tools (P09.T3 on), and any guard or limit on `/api/v1` (P09.T7).
