# Workflow

The steps, the five groups, the rules and the moves a ticket may make. It does not store tickets: Ticketing owns the current step and asks Workflow before every move. It owns the tables `wf_step`, `wf_rule_set` and `wf_transition`. Its Api is `StepQueries`, `StepOccupancy`, `TransitionPolicy`, `TurnRules` and `WorkflowPermission`. It may use the Api of Organization. Every new organization gets the eight core steps and the default rule set in the transaction that creates it, through `Application\SetUpOrganizationWorkflow` (an `Organization\Api\OrganizationSetupStep`, [ADR-0036](../../docs/03-adr/0036-organization-setup-steps-in-the-creating-transaction.md)); organizations made before that got them from the migration `Version20261110140000`. Built so far of the Api: `StepQueries` (`stepsFor` a team in the groups' list order, then origin (core, company, team), then position, then id; `groupOf` a step, removed ones included), implemented with plain SQL by `Infrastructure\Doctrine\DbalStepQueries`; `StepOccupancy` (`openTicketsIn` a step, asked by `Application\RemoveStep`), which Ticketing implements, as Workflow may not call Ticketing; `WorkflowPermission` (`STEP_CHANGE_TEAM`, `RULES_CHANGE_TEAM` on a `TeamId`), decided by `UI\Voter\WorkflowVoter` through `Application\StepChangeRights`: the team's Lead changes its steps under the step policy `extend` or `team` and its rules under `team`. Company steps, the organization's rules and the policy itself ask Organization's `ORG_ADMIN`. Built commands: `Application\AddStep`, `RemoveStep` and `SetRule`, for a company step or rule (no team) or a team's. `SetRule` writes only the switched rule's column (`DbalRuleSets::switchRule`: `INSERT … ON CONFLICT DO UPDATE SET` that one column, picked from a fixed map of the rule codes), so two people switching different rules at once keep both changes; a team row that does not exist yet starts as a copy of the organization's rules with that one rule switched.
