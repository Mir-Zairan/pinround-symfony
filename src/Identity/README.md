# Identity

Users and how they sign in: invites, passwords, two-factor login, Microsoft login and API tokens. It owns the tables `idn_user`, `idn_credential`, `idn_password_reset`, `idn_mfa_secret`, `idn_sso_identity`, `idn_api_token`, `idn_login_attempt`, `idn_oauth_client`, `idn_oauth_authorization_code` and `idn_oauth_refresh_token`. Sessions live in Valkey. Its Api is `CurrentUser` (built: the logged-in user of the request or of a security token, `Infrastructure\Security\SymfonyCurrentUser`), `CurrentTimeZone` (built: the logged-in user's saved time zone, UTC when nobody is logged in or none is saved; `Infrastructure\Security\SymfonyCurrentTimeZone`), `UserQueries` (built: `idByEmail`, `byIds`, which gives each known user's `UserView` (id, display name, first name) in one query, and `emailsOf` and `timeZonesOf` for Organization's member queries; none limits users to the tenant, as they are global; `Infrastructure\Doctrine\DbalUserQueries`), `InvitedPersonRegistration` (built: creates an active user and its password for the invite accept page in the caller's transaction, or throws `RegistrationRefused` listing `RegistrationRefusal` cases before any write, or EmailTaken alone with the EntityManager closed when another transaction took the email at the same moment; `isValidEmail` says whether an address passes the account email rule, so InviteMember refuses what accepting would; `Application\RegisterInvitedPerson`), `LoginAssurance` (built: whether a security token is a password session, only the form login's `UsernamePasswordToken` is, whether its user has two-step login on, and whether they typed a code in this session within N seconds and not before it was last turned on; `Infrastructure\Security\SymfonyLoginAssurance`, through `RecentAuth`), `TwoStepProofPages` (built: the paths of "Confirm it's you" and of the setup page with the way back, for Organization's admin gate; `UI\Controller\RecentAuthRedirects`), `LoginAssurance::isTokenAuthenticated` (built, P09.T1: whether a security token is the `ApiTokenAuthentication` a personal access token login creates) and `CurrentApiToken` (built, P09.T1: `access()` gives the request's `ApiTokenAccess`, the token id, its organization, its scope names and `expiresAt`, the instant it stops working in UTC, null for a browser session or nobody logged in; `Infrastructure\Security\SymfonyCurrentApiToken`) and `OrganizationApiTokens` (built, P09.T1: the tenant's tokens for its Admins, used by Organization's Admin › People; `Application\ApiTokensOfOrganization`; it does not check who asks, the caller's voter has). `OrganizationApiTokens::livePage` gives one keyset page of every person's personal tokens that are neither revoked nor expired (OAuth access tokens are left out, `ApiToken::isPersonal`), as `OrganizationApiToken` (id, owner id, name, display prefix and expiresAt; never the token or its hash), the soonest to expire first by expires_at then id, at most `MAX_PAGE_SIZE` (100) and throwing `InvalidArgumentException` before any query for a limit outside 1..100, half a cursor or a cursor id that is not a UUID; `revokeAsAdmin` revokes any token of the tenant, expired ones too, through `RevokeApiToken::asAdmin`, publishing `ApiTokenRevoked` with the Admin as actor and the owner as user only when that call revoked it, and throws `ApiTokenNotInOrganization` for a malformed id or one of no token of the tenant, which Organization answers with 404. `Infrastructure\Scheduler\QueueApiTokenExpiryWarnings` (once a day) warns each owner by email in the 8 days before a token stops working, only for a token that lives longer than 8 days and never for one already expired when its page is handled: it finds the organizations through the resolver `organizations_with_expiring_api_tokens` and sends one `SendApiTokenExpiryWarnings` per organization with a `TenantStamp` to `async_notify`; its handler claims up to 100 tokens with `ApiTokens::claimExpiryWarnings` (once per token, `expiry_warned_at`), queues one `Infrastructure\Mail\ApiTokenExpiryMail` per owner after the bus commits and sends itself again while a page is full. `Infrastructure\Security\TokenAuthenticator` (built, P09.T1, not an Api) authenticates the stateless `api_token` firewall of `/mcp` and `/api/v1` by the `Authorization: Bearer pr_…` header alone: a live token makes the request its user's with the token's organization as tenant and records its use at most once a minute; anything else gets the same 401 and leaves no tenant. `UI\Voter\AdminNeedsBrowserSessionVoter` denies a token actor every `ADMIN_*` attribute and `ORG_ADMIN` and `ORG_INVITE`, and `OwnAccountVoter` denies it `ACCOUNT_EDIT_OWN` (ADR-0021). Personal access tokens are stored (P09.T1): `Application\IssueApiToken` issues one and returns `IssuedApiToken`, whose plain token is shown once; it refuses a 21st personal token that still works per person and organization with `TooManyApiTokens`, counting under a per-person advisory lock in the caller's transaction. OAuth access tokens are left out of that personal cap (`ApiToken::isPersonal`) but still count when an access token is issued: `issueForOAuthClient` and `renewForOAuthClient` count live tokens of both kinds and refuse at 20, which `IssueOAuthTokenPair` answers with invalid_grant and `TOO_MANY_TOKENS`, naming both the tokens page and signing out of a connected app. `ApiTokens` (`DoctrineApiTokens`) is the module's own repository, not an Api; for the Admin list it offers `byId` (any person's token of the tenant, null for a malformed or unknown id) and `livePage` (the keyset page above, with no cap of its own); the hash is HMAC-SHA256 keyed by `API_TOKEN_PEPPER` (`HmacApiTokenHashing`, ADR-0043). The tokens page is built (P09.T1): `/me/tokens` (`UI\Controller\TokenController`, "API tokens" in the avatar menu) lists the person's own personal tokens that still work in the organization they work in, newest first (`ShowApiTokens::liveOf` over `ApiTokens::liveForUser`, which leaves out revoked and expired ones and OAuth access tokens, though those still count when an app connects or refreshes); makes one behind `RequiresRecentAuth` with `IssueApiToken::issueWithScopeNames`, which returns `NewApiToken`, and shows its plain token and the `claude mcp add` line in that response only, each with a Copy button (Stimulus `copy-text`, shown only where the browser can copy); and revokes one with `RevokeApiToken`, where another person's, another organization's, an unknown or a malformed id is the same 404. The form starts with Claude Code's default scopes ticked (`read`, `rounds:write`, `ApiTokenScope::claudeCodeDefaults`) and offers `comments:write`, `tickets:move`, `reports:write` and `notebooks:write` unticked. A token-authenticated request never reaches the page: the main firewall reads no Bearer header, and `OwnAccountVoter` denies a token actor `ACCOUNT_EDIT_OWN`. Two-step login setup is built (P01.T6 step 1): `/me/security/two-step` turns it on with a QR code drawn on the server, a code from the app and 10 recovery codes shown once (`StartTwoStepSetup`, `ConfirmTwoStepSetup`, entity `TwoStepLogin` on `idn_mfa_secret`). Login step two is built (P01.T6 step 2): for a user with two-step login on, the right password only starts a pending login (`PendingLogin`, `Infrastructure\Security\SymfonyPendingLogin`, started by the listener `AskForTwoStepCode`), and `/login/code` (`LoginCodeController`) takes a code from the app or one recovery code (`AcceptTwoStepCode`) and finishes the login; every login records its times per user in the session (`SessionConfirmations`). "Confirm it's you" is built (P01.T6 step 5): an action marked with SharedKernel's `RequiresRecentAuth` opens only after the password and a code in this session within 10 minutes (`RecentAuth`); the UI listener `AskToConfirmItsYou` sends anyone else to `/me/confirm` (`ConfirmItsYouController`, `ConfirmItsYou`), or, while two-step login is off, to its setup page. Turning it off is built (P01.T6 step 4): `/me/security` asks for the password and a code (`SecurityPageController`, `DisableTwoStepLogin`), deletes the `idn_mfa_secret` row and removes the session's proofs. The admin gate is built (P01.T6 steps 3 and 6): admin pages need two-step login on and a code of the last hour in this session, checked by Organization's `AdminAreaVoter` through `LoginAssurance`; a code proof counts for admin pages and `RequiresRecentAuth` only while two-step login is on and only from the second it was last turned on. A new display name saved by `UpdateProfile` publishes `Api\Event\UserRenamed` on event.bus through `Application\IdentityEvents` (`Infrastructure\Messenger\MessengerIdentityEvents`); it is an `Api\Event\IdentityEvent`, which goes to the outbox in the change's transaction and on to `async_notify`, so Organization clears its team people cache only once the relay and worker-notify have handled it, and the old name can show until then. The same way, `IssueApiToken` publishes `Api\Event\ApiTokenIssued` and `RevokeApiToken` publishes `Api\Event\ApiTokenRevoked` (only when that call revoked it), with ids, scope names and times only, for the audit log. OAuth client registration and discovery are built (ADR-0050): `POST /oauth/register` (`UI\Controller\OAuthClientRegistrationController`, `Application\RegisterOAuthClient`) registers a public client only (RFC 7591: `token_endpoint_auth_method` "none", no secret, the code flow with authorization_code and optionally refresh_token, 1 to 5 redirect URIs that are https, http on localhost, 127.0.0.1 or [::1], or the extension's `https://<id>.chromiumapp.org/` (`Domain\OAuthRedirectUri`), a client_name of at most 100 characters) into `idn_oauth_client` (`Domain\OAuthClient`, `DoctrineOAuthClients`), answering 201 with the stored metadata, 400 `invalid_client_metadata` or `invalid_redirect_uri`, or 429 with Retry-After past `oauth_client_registration_per_ip` (30 an hour, every request counted, refused ones too), never cached. The table is global (no organization_id, no row-level security; the organization is picked per grant on the consent page), and pinround_app has SELECT and INSERT only. `GET /.well-known/oauth-authorization-server` (RFC 8414) and `GET /.well-known/oauth-protected-resource` (RFC 9728, for `/mcp`) (`UI\Controller\OAuthDiscoveryController`, `Application\OAuthDiscovery`) give absolute URLs on the request's origin and run under the `oauth_discovery` firewall without security, so no session turns their `max-age=3600, public` private. All three need no login and no chosen organization (`organization.routes_without_organization`). The consent page is built (ADR-0050): `GET /oauth/authorize` (`UI\Controller\OAuthConsentController`, `Application\AuthorizeOAuthClient`) shows the app's name, the host it sends the person back to, what each asked scope lets it do and the person's current organizations, behind `RequiresRecentAuth` and `OwnAccountVoter`'s `EDIT_OWN`, never cached; an unknown client or a redirect URI it did not register gets an error page and no redirect, and any other bad request goes back to the app with the RFC 6749 error and the state; its CSRF-checked Allow saves a 60-second single-use code for the picked organization in `idn_oauth_authorization_code` (tenant table, hash only, with the client, redirect URI, S256 challenge and scopes) and sends the code and state to the redirect URI, Deny sends `access_denied`, and an organization the person is not in is 404 with no code. Only the consent form's page adds the redirect URI's origin (`UI\OAuthRedirectOrigin`, the exact port on a loopback, none for `[::1]`) to its `form-action` through SharedKernel's `CspFormActionOrigin`, so the browser lets Allow and Deny redirect there; its error pages keep `form-action 'self'`. The token endpoint is built (ADR-0050): `POST /oauth/token` (`UI\Controller\OAuthTokenController`, `Application\ExchangeOAuthAuthorizationCode`) trades a code, once, for the client that got it with exactly its redirect_uri and the PKCE verifier of its S256 challenge, for an access token of 1 hour (`ApiToken::OAUTH_ACCESS_LIFETIME_SECONDS`, a `pr_` row of `idn_api_token` for the code's person and organization, so it works on `/mcp` and `/api/v1` like a personal access token) and a refresh token of 30 days (`prr_`, `Domain\OAuthRefreshToken` in `idn_oauth_refresh_token`, hash only, sent only to a client that registered the refresh_token grant); refused requests answer RFC 6749 JSON with 400, more than 300 requests per IP in 15 minutes (`oauth_token_per_ip`, token and revoke together) 429 with Retry-After, and every answer is `Cache-Control: no-store`. A refresh rotates (`Application\RefreshOAuthTokens`): the refresh token is marked used, the access token issued with it is revoked and a new pair of the same family is issued, under the family's lock; a used refresh token that comes back, or a used code that comes back, revokes its whole family, and both stop once the person has left the organization. `POST /oauth/revoke` (`Application\RevokeOAuthToken`, RFC 7009) lets a client revoke only its own tokens, a refresh token with its whole family and an access token alone, and answers 200 with an empty body whatever the token was. `UI\OAuthEndpointCors` lets the browser extension read the answers of `/oauth/register`, `/oauth/token`, `/oauth/revoke` and `/.well-known/oauth-authorization-server`: an origin of `EXTENSION_ORIGINS` (SharedKernel's `ExtensionOrigins`, the same list as `/api/v1`) gets its own origin in `Access-Control-Allow-Origin`, never `*` or credentials, and a preflight answered 204 before the router; any other origin gets no CORS header and the router's 405 to a preflight; every answer has `Vary: Origin`. It may use the Api of SharedKernel only.
